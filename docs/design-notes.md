# Brack 設計メモ

実装時の判断とその理由、調査の結果をまとめたものです。使い方は [README](../README.ja.md) を、ビルドの詳細とテストは [development.ja.md](development.ja.md) を参照してください。

## 1. プラグイン形式の抽象化

### 構成

- `PluginInstance`（`src/core/plugin/plugin.h`）を形式共通の基底クラスにし、CLAP / VST2 / VST3 がそれぞれ派生クラスを実装します。エンジンはプラグインを `HostedPlugin` 越しに見るので、形式も、どのプロセスで動いているかも意識しません（15 章）。
- 基底クラスが持つもの: 活性化状態、オーディオスレッドとの停止／開始ハンドシェイク、音声バッファ、エディタ、表示名。
- 形式ごとの処理はフック（`initPlugin`、`processPlugin` など）として実装し、基底クラスはこれらを、クラッシュを封じ込める `callPlugin()` 越しに呼びます（11 章）。
- 理由: 停止要求と応答、活性化の順序、処理失敗時の扱いを形式ごとに書くと食い違いが出るので、テンプレートメソッドにして一か所に置きました。
- 派生クラスのデストラクタは最初に `shutdown()`（エディタを閉じて非活性化）を呼びます。基底クラスのデストラクタからは派生側の仮想関数を呼べないためです。

### イベント表現

- エンジン内部の MIDI は、CLAP のイベント構造体（`InputEventList`）で表します。
- CLAP にはそのまま渡し、VST2 / VST3 には `processPlugin` の中で各形式のイベントへ変換します。
- 理由: CLAP の MIDI / SysEx イベントは生のバイト列をそのまま持てるので、Brack の「MIDI を変換しない」方針に最も合います。リアルタイムに安全な既存の実装（固定長の配列と SysEx 用アリーナ）もそのまま使えます。

### エディタ

- エディタのウィンドウ（`HostWindow`。トップレベルか、アプリのウィンドウの子。12 章）を全形式で共有します。各形式はコールバック（ユーザーによるリサイズ、DPI 変更、閉じる操作）を自分のエディタ API につなぎます。
- ユーザーが閉じたときは、その場では隠すだけにし、破棄はホストスレッドへ後回しにします（`editorClosedByUser`）。ウィンドウプロシージャやプラグインの呼び出しの中で破棄しないためです。
- 後回しにした破棄は、エディタの世代番号で照合します。閉じてすぐに開き直したエディタを誤って閉じないためです。
- **DPI（Windows）。** brack.exe（GLFW が設定する）、brack-cli.exe、プラグインホストは、プロセス全体を per-monitor DPI 対応（v2）にします。エディタはホストスレッドで作り、ホストスレッドはプロセスの設定に従います。brack.dll を使うアプリでは、アプリの設定に従います。
  - ホストスレッドだけを per-monitor にするのでは足りません。JUCE のエディタはプロセスの設定を見て拡大を決めるので、ウィンドウの大きさは正しくても中身を大きく描き、はみ出します（175% の画面の、JUCE の CLAP プラグイン）。
- **開くときの大きさ（CLAP）。** 親ウィンドウを受け取ってから本当の大きさが分かるエディタ（JUCE のもの）は、`set_parent` や `show` の中で `request_resize` を呼びます。その時点ではエディタがまだ登録されていないので、この要求には応じられません。そこで、開き終えたら `get_size` で大きさを聞き直し、違えばウィンドウを合わせます。
  - VST3 はウィンドウを作ってから `attached` を呼ぶので、その中の `resizeView` も受けられます。VST2 は `effEditOpen` の後に大きさを聞き直します（2 章）。

### 形式の判定とプラグイン ID

- 形式はファイルの拡張子で決めます（`.clap` / `.vst3` / VST2 は Windows では `.dll`。OS ごとの規則は 13 章）。パスだけで決まるので、セッションに形式を別途保存する必要がありません。
- ファイル内のプラグイン ID:
  - CLAP: CLAP の ID。
  - VST3: クラス ID を Steinberg の表記（`FUID::toString` や moduleinfo.json と同じ、32 ビット語 4 つの 16 進）で書きます。Windows の TUID はバイト順が COM 互換なので、バイト列をそのまま 16 進にするとプラットフォームによって表記が変わるためです。
  - VST2: ユニーク ID を、表示できれば 4 文字、できなければ `0xXXXXXXXX` で書きます。
- この ID は `PluginConfig::pluginId` に入れ、セッションには `"pluginId"` で保存します。状態取得の JSON には `"pluginId"` と `"format"` が入ります。
- セッションと GUI の設定には版を書きません。読むところが無いためです。

## 2. VST2 ホスト（`src/core/vst2/`）

- ヘッダーは Xaymar/vst2sdk v0.4.0 です。ただし実際のプラグインと食い違う定義があるため、Brack が使う部分は `vst2_abi.h` の定義で置き換えています（6 章）。
- `vst.h` はグローバル変数を 2 つ定義しているので、インクルードするのは 1 つのビルド対象につき 1 翻訳単位だけです（Brack では `vst2_plugin.cpp`、テストではテスト用プラグイン）。

### 生成とシェル

- エフェクトのポインタが決まる前（`VSTPluginMain` の実行中）にもホストコールバックは呼ばれます。そのため、生成中のインスタンスとシェル内のプラグイン ID をスレッドローカル変数で渡します。生成後は `AEffect::user`（vst2sdk の `host_internal`）でインスタンスを引きます。
- シェル（1 つの DLL に複数のプラグイン）:
  - ID を指定して生成してもシェルが返ってきた場合は、プラグインを列挙して目的の ID（未指定なら先頭）で生成し直します。
  - シェルの判定と列挙の前に `effOpen` を呼びます。開く前の問い合わせに応じないシェルがあるためです。
- シェルでないプラグインの ID が保存時と違っていても、警告を出して読み込みます。プラグインの更新で ID が変わったとき、セッションが開けなくなるのを避けるためです。

### 状態

- 先頭に `BRV2` と種別 1 バイトを置きます。
  - `C`: `effGetChunk` のバンクチャンク（チャンク対応のプラグイン）。全プログラムを含めるため、プログラムではなくバンクを保存します。
  - `P`: 現在のプログラム番号と全パラメーターの値（チャンク非対応のプラグイン）。

### 処理

- MIDI と SysEx は、バイト列を変えずに VST2 のイベントにして、処理の直前に `effProcessEvents` で渡します。
- 入力バッファも出力バッファも毎ブロック 0 で埋めてから処理を呼びます。入力をその場で書き換えるプラグインや、無音のときに出力に書かないプラグインがあるためです。
- `effFlagsCanReplacing` が無いプラグインには、旧式の加算型の `process` を使います。

### ホストコールバックの応答

- 時刻情報（`audioMasterGetTime`）は 0（情報なし）を返します。Brack にはトランスポートが無く、vst2sdk には時刻情報の構造体（`VstTimeInfo`）の定義もありません。
- 処理レベル（`audioMasterGetCurrentProcessLevel`）は、オーディオスレッドなら 2（リアルタイム）、それ以外は 1 を返します。4 はオフラインレンダリングを意味するので返しません。
- プラグインが送る MIDI（8 番）は受け付けますが、使いません。
- 入出力の変化（`audioMasterIOChanged`）はホストスレッドで扱います。非活性ならその場でポートを読み直し、活性中なら再起動を予約します。

### エディタ

- サイズは固定です。VST2 にはホスト側からリサイズする標準の手段が無いためです。プラグインからのサイズ変更要求（`audioMasterSizeWindow`）には追従します。
- `effEditOpen` の戻り値は信用しません。正常に開いても 0 を返すエディタが多いためです。開くまでサイズを知らないエディタがあるので、開いた後にもう一度サイズを問い合わせます。
- `effEditIdle` は約 10 ms ごとのアイドル処理で呼びます。

## 3. VST3 ホスト（`src/core/vst3/`）

- ヘッダーは steinbergmedia/vst3_pluginterfaces v3.8.1 です（5 章）。
- インターフェース ID は `vst3_iids.cpp` の 1 翻訳単位で定義します（`INIT_CLASS_IID`）。この翻訳単位と `funknown.cpp` を `brack_dep_vst3` にまとめ、テスト用 VST3 プラグインも同じものをリンクします。
- pluginterfaces のヘッダーは互いに `"pluginterfaces/..."` でインクルードし合います。そのため取得先のフォルダ名を `pluginterfaces` にし、その親をインクルードパスにしています。

### コンポーネントとコントローラー

- コンポーネントが `IEditController` を実装していれば一体型として扱い、そうでなければ別のコントローラーを生成します。
- 別オブジェクトの場合は、`IConnectionPoint` を双方向に直接つなぎます（プロキシは挟みません）。
- 初期化後に、コンポーネントの状態をコントローラーへ渡して同期させます（`setComponentState`）。
- コンポーネントが使う `IMessage` / `IAttributeList` は、ホストの `IHostApplication::createInstance` で作ります。

### パラメーターの受け渡し

- コントローラーからの変更（`performEdit`）は、キューを通して次の `process` の入力パラメーター変更に入れます。
- 処理側の出力パラメーター変更と、MIDI CC から変換した変更は、別のキューでホストスレッドへ戻し、アイドル処理でコントローラーに `setParamNormalized` します。エディタの表示を揃えるためです。
- どちらのキューも、書き込み側はミューテックスで直列化し、読み出し側（オーディオスレッドまたはホストスレッド）は待ちません。

### MIDI の変換

VST3 は生の MIDI を受け取れないため、次のように変換します。

| MIDI | VST3 での扱い |
|---|---|
| ノートオン／オフ | ノートイベント（ベロシティ 0 のノートオンはノートオフ） |
| ポリフォニックキープレッシャー | ポリプレッシャーイベント |
| SysEx | データイベント（バイト列はそのまま） |
| CC、ピッチベンド、チャンネルプレッシャー、プログラムチェンジ | プラグインが `IMidiMapping` で割り当てたパラメーターの変更。割り当てが無ければ届かない |
| システムコモン／リアルタイム | 届かない |

- `IMidiMapping` はコントローラー側のインターフェースで、オーディオスレッドからは呼べません。そこでバス × チャンネル × コントローラー番号の対応表をホストスレッドで作り、まとめてアトミックに差し替えます。古い表は、オーディオスレッドが参照しなくなる非活性化の時点で破棄します。
- `kMidiCCAssignmentChanged` を受けたら対応表を作り直します（再起動はしません）。
- プログラムチェンジの値は、割り当て先パラメーターのステップ数で正規化します。

### 活性化と処理

- `setupProcessing` の後、音声出力バスとイベント入力バスをすべて有効にします。音声入力バスは有効にしませんが、どのバスにも無音のバッファを渡します。
- 再生情報は「停止中・120 BPM・4/4」を渡します（Brack にはトランスポートが無いため）。
- 無音フラグが立った出力チャンネルは 0 で埋めます。フラグを立てたチャンネルに書かないプラグインがあるためです。
- `restartComponent`: `kIoChanged` はポートの読み直し、`kReloadComponent` と `kLatencyChanged` は再起動の予約として扱います。

### 状態

- 先頭に `BRV3` を置き、続けてコンポーネントの状態とコントローラーの状態を、それぞれ 8 バイトの長さ付きで並べます。
- 読み込みでは、コンポーネントに状態を渡した後、同じデータでコントローラーを同期し（`setComponentState`）、最後にコントローラー自身の状態を渡します。

### エディタ

- `IPlugFrame::resizeView` を受けたら、ウィンドウのサイズを変えてから `onSize` を呼びます。
- ユーザーのリサイズは `checkSizeConstraint` で補正してから `onSize` に渡します。
- `IPlugViewContentScaleSupport` に対応したプラグインには、開くときと DPI が変わったときに倍率を渡します。
- `hasGui()` は、コントローラーがあれば真を返します。ビューを実際に作るまでエディタの有無は分からないためです。エディタが無ければ、開くときにエラーになります。

## 4. スキャン

- **探す場所:** 各形式の標準フォルダと環境変数（`CLAP_PATH` / `VST3_PATH` / `VST_PATH`）。VST2 はレジストリの `VSTPluginsPath` も見ます（Windows の詳細は 10 章）。
- **フォルダの扱い:** `.vst3` フォルダ（バンドル。macOS では `.clap` と `.vst` も）は 1 つのプラグインとして扱い、中には入りません。
- **個々の項目のエラー:** 個々のファイルの情報が取れなくても、フォルダの巡回は止めません。
- **VST2 の DLL:** 読み込む前に PE ヘッダーからエクスポートを読み、`VSTPluginMain`（または `main`）を持つものだけを読み込みます。プラグインフォルダには補助 DLL も置かれていて、`LoadLibrary` すると DllMain が走るためです。同じ方法で、別のアーキテクチャ用の DLL も見分けます（下記）。
- **プラグインホストプロセスで調べる:** ファイルは、そのアーキテクチャのプラグインホストプロセスで調べます（15 章）。調べている途中でプラグインが落ちても止まっても、そのファイルの失敗になるだけです。Brack と同じアーキテクチャのプラグインホストが無いときだけは、Brack のプロセス内で調べます（そのとき防げないことは 9 章）。
- **VST2 は生成して調べる:** VST2 の名前やインストゥルメントかどうかは、インスタンスを作らないと分かりません。生成と問い合わせは構造化例外で保護し（`runGuarded`）、落ちたプラグインは飛ばして破棄もしません。
  - VST3 はファクトリへの問い合わせだけで済み、インスタンスは作りません。
  - DLL の読み込み自体（DllMain）は保護していません。ロックを持ったまま例外で抜けるとデッドロックするためです。プラグインホストで調べるので、ここで落ちても終わるのはそのプロセスだけです。
- **別のアーキテクチャ用のプラグイン:** PE ヘッダーのマシン種別、または VST3 バンドルの中のフォルダでアーキテクチャを決め、そのアーキテクチャのプラグインホストで調べて一覧に載せます。
  - プラグインホストが無い場合（ARM64 用のプラグインなど）は、読み込もうとせずに飛ばし、詳細ログ（Debug）にだけ記録します。こうしたプラグインは複数のビルドが探す共通の場所にあるので、毎回警告すると邪魔になるためです。
  - アーキテクチャはヘッダー（Windows と Linux の VST3 バンドルでは中のフォルダ）を見るだけで決まるので、キャッシュの項目を使うファイルでもスキャンのたびに決め直します。キャッシュにも書きますが、読み込んだ値は使いません。VST3 バンドルのどのバイナリを使うかはビルドごとに違い、キャッシュはどのビルドも同じファイルを使うためです（10 章）。
- **スキャンキャッシュ:**
  - GUI は起動するたびにスキャンするので、結果を `%APPDATA%\brack\plugin-cache.json` に保存します。どのアーキテクチャのビルドも同じファイルを使います（10 章）。
  - サイズと更新時刻（バンドルは中の全ファイルの合計と最新）が変わっていないファイルは、読み込まずにキャッシュを使います。
  - 更新時刻は、Linux では負の値になります（libstdc++ のファイル時刻は 2174 年から数える）。そのため、最新の時刻を求めるときに 0 から始めてはいけません。時刻がいつも 0 になり、大きさを変えずに更新されたファイルを見逃します。
  - 保存するのは成功した結果だけです。失敗したファイルは毎回調べ直し、ライセンスを直した場合などに回復できるようにしています。
  - CLI のスキャンはキャッシュを使いません。DLL では、アプリがキャッシュファイルを指定できます（`brack_scan_plugins`、12 章）。
- **GUI の一覧:** スキャン結果のうち音源（インストゥルメント）だけを並べます。エフェクトは「From file...」から読み込めます。

## 6. 調査: vst2sdk と公式ヘッダーの違い

### 比較の方法

- Steinberg は VST2 SDK の配布を 2018 年に終えています。Steinberg の GitHub（vst3_pluginterfaces、vst3_public_sdk）の全履歴にも、`aeffect.h` / `aeffectx.h` はありません。
- 代わりに、独立に作られた次の 2 つと比べました。
  - **FST**（リバースエンジニアリングの手順を文書化したもの。比べたコピーには手修正が入っている）
  - **VeSTige**（Carla に同梱。LMMS と Carla が実際のプラグインのホストに使っている）
- 構造体のサイズ、フィールドのオフセット、オペコードと定数の値を、x64 と x86 の両方で比べました。
- FST と VeSTige が揃って Xaymar と違う箇所は、Xaymar が実際の取り決めと違うと判断しました。

### 結果

| 項目 | Xaymar | FST / VeSTige | Brack での扱い |
|---|---|---|---|
| イベント一覧（`vst_events_t`） | `int32 count; int32 reserved; vst_event_t** events;`（オフセット 8 にポインタ配列へのポインタ） | `int32 numEvents; <ポインタ幅> reserved; VstEvent* events[2];`（x64 では 16、x86 では 8 から構造体の中に並ぶ） | `vst2_abi.h` で補正。Sound Canvas VA のクラッシュの原因（7 章） |
| プラグインからホストへのイベント送信 | `VST_HOST_OPCODE_EVENT = 9` | `audioMasterProcessEvents = 8`（9 は廃止された `audioMasterSetTime`） | 8 番で扱うよう補正 |
| ホストコールバックの `value` 引数 | `int64_t` | ポインタ幅の整数 | `intptr_t` で補正。x64 では同じだが、32 ビットでは以降の引数がずれる |
| パラメーター情報の構造体 | `largeStepInteger` にあたる int32 が無く、148 バイト | 152 バイト | Brack は使わないので補正していない |
| スピーカー配置の構造体 | スピーカー 32 個分（3592 バイト） | 8 個分（904 バイト） | 使わない。可変長なので `sizeof` でコピーしなければ問題は出ない |
| 処理レベルの値 4 の意味 | USER（ユーザー操作のスレッド） | オフライン | 使わない（Brack は 1 か 2 を返す） |
| 時刻情報 | 構造体もオペコード 7 の定義も無い | あり | 0 を返す |

- 一致を確かめたのは、プラグイン本体の構造体（`AEffect`。全フィールドのオフセットと、x64 で 192 バイトの全体のサイズ）、MIDI イベントと SysEx イベント、エディタの矩形、ピン情報、スピーカー 1 個分の情報、Brack が使うエフェクト側オペコード、ホスト側オペコードのうちイベント送信以外の比べたもの、フラグ、カテゴリ、イベント種別、マジック番号です。
- x86 では、イベント一覧の先頭ポインタのオフセットが偶然 8 で一致します。それでも Xaymar の定義ではそこに「配列へのポインタ」が入るので、プラグインはそれを最初のイベントとして読んでしまいます。

## 7. 調査: Sound Canvas VA のクラッシュ

- **症状:** GUI で Roland Sound Canvas VA（VST2）を使うと Brack が落ちました。Windows のイベントログでは、毎回 `SOUND Canvas VA.dll` の同じ箇所でのアクセス違反（0xc0000005）でした。
- **結果:** オーディオデバイスも MIDI ポートも開かない手動レンダリングで再現しました。無効なアドレス `0xFFFFFFFFFFFFFFFF` の読み込みで、呼び出し元は `Vst2Instance::processPlugin` でした。無音のうちは落ちず、最初のノートを送ったところで落ちました。
- **原因:** Brack が Xaymar の `vst_events_t` の形でイベント一覧を渡していたため、プラグインは構造体の外の未初期化の領域を最初のイベントへのポインタとして読んでいました（6 章の表の 1 行目）。
- **テストで見つからなかった理由:** テスト用の VST2 シンセも同じヘッダーで書いていたので、ホストとシンセが同じ誤りを共有していました。現在はどちらも `vst2_abi.h` を使います。オフセットはコンパイル時にチェックしているので、並びがずれればビルドで気づけます。

## 9. 既知の制約

- Brack にはトランスポートが無いため、テンポ同期するプラグインは 120 BPM・停止中として動きます（VST2 は時刻情報なし）。
- VST3 では、`IMidiMapping` に割り当ての無い CC などと、システムメッセージは届きません。
- ほかのアーキテクチャのプラグインは、そのアーキテクチャのビルドのプラグインホストがあり、その PC がそのアーキテクチャを実行できるときだけ動きます（15 章）。
- Brack と同じアーキテクチャのプラグインホストが無いときはスキャンを Brack のプロセス内で行うので、DllMain でのクラッシュや、生成時に止まってしまうプラグインは防げません（4 章）。
- 修正の入っていない MidiSrv は、仮想デバイスを削除するとデッドロックします（microsoft/MIDI#1047。修正は 2026 年 11 月下旬の Windows 更新で配られる予定）。
  - 原因: MidiSrv は仮想デバイスを閉じる処理（`CMidiClientManager::DestroyMidiClient`）を、クライアント管理ロックを排他取得したまま実行します。その途中で同じロックを共有取得しようとして、自分自身を待ち続けます。SRW ロックは再入できないためです。
  - 影響: 以後、システム全体で MIDI ポートを開く処理も閉じる処理も、すべてこのロック待ちで止まります。仮想ポートが 2 つ以上あると、最初のポートの削除でサービスが止まるので、2 つ目以降のポートは削除されずに残ります。
  - Brack の対策: 終了時に必ず正しい手順で解放し、サービス呼び出しにはすべてタイムアウトを設けています。該当ビルドを検出すると、GUI（仮想ポート追加欄）と `brack-cli virtual-check` で警告を表示します。サービスが止まったことを検知した後は、残りのポートの解放待ち（各 5 秒）を省いてすぐに終了し、新しい仮想ポートの作成も即座にエラーにします。不具合そのものは回避できません。
  - 該当ビルドの見分け方: MidiSrv が読み込む仮想トランスポートの DLL（`Midi2.VirtualMidiTransport.dll`）に、`OnDeviceDisconnectedAlwaysTeardown` という文字列があるかを見ます。修正では、MidiSrv.exe のロックの変更と一緒に、この DLL の `MidiEndpointTable::OnDeviceDisconnected` がこの名前の関数に置き換わります。どの関数も `__FUNCTION__` をトレースに書くので、修正済みの DLL にはこの名前が入ります。DLL が無ければ（仮想トランスポートが無い）警告しません。

## 10. 32 ビット版

- x86 でもビルドでき、.NET のテスト（`dotnet`。8 章）を除いて同じテストが通ります。ビルド手順は development.ja.md にあります。
- 32 ビットで初めて表に出た問題と、その対処:
  - **VST3 のエクスポート名:** 32 ビットの `__stdcall` 関数は、`extern "C"` でも名前が装飾されます（`_GetPluginFactory@0`）。実際の 32 ビット VST3 は装飾なしの `GetPluginFactory` でエクスポートしているので、ホストはその名前で探します。テスト用 VST3 シンセは `.def` ファイルで装飾なしの名前をエクスポートします。
  - **VST3 バンドル内のフォルダ:** 32 ビットでは `Contents\x86-win` です（64 ビットは `Contents\x86_64-win`）。
  - **VST2 のホストコールバック:** `value` 引数をポインタ幅にしました（6 章）。
  - **レジストリのリダイレクト:** 32 ビットのプロセスでは、`HKLM\SOFTWARE` の読み取りが `WOW6432Node` へリダイレクトされます。
    - Windows MIDI Services の設定（64 ビットのサービスのもの）は、64 ビット側のビュー（`KEY_WOW64_64KEY`）で読みます。
    - VST2 の `VSTPluginsPath` は、リダイレクトに任せず、64 ビット側と 32 ビット側の両方を読みます（`KEY_WOW64_64KEY` と `KEY_WOW64_32KEY`）。どちらのアーキテクチャのプラグインも、そのプラグインホストで動かせるためです。
  - **System32 のリダイレクト:** 32 ビットのプロセスでは、System32 へのアクセスが SysWOW64 へリダイレクトされます。MidiSrv の不具合（#1047）の判定で読む DLL は 64 ビットのサービスが読み込む本物なので、`Sysnative` 経由で読みます。そうしないと、32 ビット版で警告が出なくなります。
- **仮想 MIDI ポート:** 32 ビット用の Windows MIDI Services クライアント（`Midi2.MidiSrvTransport`）は、COM の登録はありますが DLL が `SysWOW64` に無く、作成は 0x80040154 で失敗します（Windows 11 26200）。32 ビット版では、使えない理由としてそれを報告します。
- **どのビルドも同じファイル:** GUI の設定（`settings.json`）とスキャンキャッシュ（`plugin-cache.json`）は、アーキテクチャによらず 1 つずつです。
  - 分けないのは、どのビルドもほかのアーキテクチャのプラグインをプラグインホストで動かし（15 章）、同じ場所を探す（下）ためです。
  - スキャンキャッシュには、このビルドが動かせないアーキテクチャの項目（x64 版にとっての ARM64 用など）も、ほかのビルドのために消さずに残します。一覧には載せません。
  - キャッシュの項目に書かれたアーキテクチャは使わず、スキャンのたびに決め直します（4 章）。
  - x86 版と x64 版の GUI を同時に開くと、同じ設定ファイルに保存し合い、あとから保存したほうが残ります（保存は一時ファイルからの置き換えなので、壊れはしません）。
- **アーキテクチャごとに分けたファイル:** テストの一時ファイル（`%TEMP%` の `brack_test_*-<arch>`）だけです。x64 と x86 のテストを同時に走らせても衝突しません。
- **探す場所はどのビルドも同じ:** `Program Files` と `Program Files (x86)` の標準の場所、`HKLM\SOFTWARE\VST` の 64 ビット側と 32 ビット側、`HKCU\Software\VST`（HKCU はリダイレクトされない）、`%LOCALAPPDATA%\Programs\Common\CLAP` / `...\VST3`、環境変数、追加フォルダです。
  - 32 ビットのプロセスでは `FOLDERID_ProgramFilesX64` などが使えないので、64 ビットの `Program Files` は環境変数 `ProgramW6432` / `CommonProgramW6432` から得ます。
  - 同じフォルダが重なっても、`findPluginFiles()` が 1 つにまとめます。
  - ほかのアーキテクチャ用のプラグインの扱いは 4 章と 15 章のとおりです。
- **保存時の一時ファイル:** `<ファイル名>.<プロセス ID>.tmp` に書いてから置き換えます。2 つの Brack が同じファイルを同時に保存しても衝突しません。

## 11. クラッシュの封じ込めと自動保存

この章の封じ込め（次の 2 節）は、プラグインを Brack と同じプロセスで動かすとき（`pluginsInProcess`）のものです。既定ではプラグインはプラグインホストプロセスで動き（15 章）、封じ込めの仕組みはそこで、落ちた場所を調べて報告するのに使います。残りの 2 節（自動保存と、セッションのパスとラック）は、プラグインをどちらで動かすときも同じです。自動保存は、封じ込められずに Brack ごと終わったときの被害を小さくするためのものです。

### プラグインのクラッシュを封じ込める（`PluginInstance::callPlugin`）

- Brack からプラグインへの呼び出しは、すべて `PluginInstance` の公開メソッドを通ります。そこで各形式の実装（フック）を `callPlugin()` で包み、構造化例外（アクセス違反、プラグインが捕まえなかった C++ 例外、スタックあふれなど）を `__try/__except` で捕まえます（`runGuarded`）。
  - スタックあふれを捕まえた後は、ガードページを戻します（`_resetstkoflw`）。次のスタックあふれも捕まえるためです。
- 捕まえたら、そのインスタンスを crashed にします。
  - 以後は一切呼びません（`callPlugin` が何もせずに偽を返す）。オーディオは無音です。
  - 破棄処理も呼ばず、モジュール（DLL）も解放せずにプロセスの終わりまで持ち続けます（`keepForever`）。落ちた時点で、プラグインのメモリやロックが壊れている可能性があるためです。
  - エディタは `abandon()` で閉じます。プラグインを呼ばずにウィンドウを隠し、コールバックを外し、プラグインの子ウィンドウはそのまま残します（破棄するとプラグインのウィンドウ処理が動くため）。
  - 状態は、最後に保存または読み込みに成功したものを返します（`saveState`）。
- 例外を捕まえたスレッド（オーディオスレッドのこともある）では、例外コード、アドレス、処理名（文字列リテラル）を書き込むだけにし、メモリ確保もログ出力もしません。ログへの出力とモジュール名の解決は、ホストスレッドのアイドル処理で行います。
- 例外の捕まえ方の都合で、プラグインと `callPlugin` の間の関数のデストラクタは走りません（`/EHsc`）。Brack 側はプラグインを呼ぶ間にロックを持たない作りなので、問題になりません。
- Linux と macOS では、シグナルで同じことをします（`plugin/library_posix.cpp`）。
  - `runGuarded` が、スレッドごとの飛び先（`sigsetjmp`）を置いてから呼びます。その間にそのスレッドで `SIGSEGV`・`SIGBUS`・`SIGILL`・`SIGFPE`・`SIGTRAP` が来ると、ハンドラーが `siglongjmp` で戻します。入れ子の呼び出しでは、内側の呼び出しが終わると、外側の呼び出しの飛び先を使うように戻します。
  - ハンドラーは別のスタック（`sigaltstack`、64 KB）で動かすので、スタックあふれも捕まえます。スレッドがすでに別のスタックを持っていれば（プラグインホストのスレッド）、それを使います。
  - 守っていないところで来たシグナルは、それまでのハンドラー（プラグインホストなら、記録して終わるもの。15 章）に渡し、無ければ既定の動作（プロセスが終わる）になります。ハンドラーは最初の守られた呼び出しのときに入れるので、プラグインホストが記録に使うハンドラー（起動直後に入れる）はそれより前に入っています。
  - `abort()`（`SIGABRT`）は捕まえません。glibc の `abort` はロックを持ったままシグナルを出すので、飛び出すとロックが残ります。Windows の `__fastfail` と同じく、プロセスが終わります。
  - 報告の例外コードはシグナルの番号です（`crashed in process: segmentation fault (0x0000000B) at libfoo.so+0x1234`）。
  - C++ の例外は `catch (...)` でも捕まえますが、効くのはプラグインと Brack が同じ C++ の実行時ライブラリを使うときだけです。Linux では、それぞれが実行時ライブラリを静的にリンクしていると（Brack のプログラムもテスト用シンセも、多くのプラグインもそう）、巻き戻しがプラグインの unwinder から Brack の unwinder に入ったところで `abort` します（テストで確認）。macOS では、Brack は実行時ライブラリを静的にリンクせず、プラグインもふつうはシステムの libc++ を使うので、捕まえられるはずです（確かめていません）。
- 封じ込められないもの:
  - プラグインが自分で作ったスレッドでの例外
  - プラグインのウィンドウ処理の中での例外（Windows がカーネルからのコールバックとして呼ぶので、例外が呼び出し元のメッセージループまで戻ってこないため）
  - `__fastfail`（ヒープ破壊の検出など）、`abort()`、`ExitProcess()`
  - Linux では、プラグインから漏れた C++ の例外（上のとおり、実行時ライブラリが別々のとき）

### モジュールの読み込み・一覧・解放のクラッシュ（`markModuleBroken`）

- インスタンスができる前のモジュール単位の呼び出し（CLAP の `clap_entry` の `init` / `get_factory` / `deinit` とプラグインの一覧、VST3 のモジュールの入口と出口、`GetPluginFactory`、クラスの一覧など）も、1 つずつ `guardedCall` で包みます。VST2 にはモジュール単位で呼ぶ関数が無く、`VSTPluginMain` はインスタンスの `init` として `callPlugin` が包みます。
- 読み込みと一覧はモジュール表のロックを持ったまま走ります。呼び出しごとに内側で捕まえるので、例外がロックの外まで抜けず、ロックはふつうに解放されます（`__try` は別の関数 `runGuardedSeh` にあり、`lock_guard` のデストラクタは飛ばされない）。
- 落ちたモジュールは、パスをキーに「壊れたモジュール」の表（破棄しない静的変数）に記録します。
  - 読み込みと一覧で落ちたものは、モジュールのオブジェクトごと表が持ち続けます。デストラクタ（`deinit` / `ExitDll` と DLL の解放）は走りません。
  - 解放で落ちたものは、オブジェクトはもう残せないので、DLL を解放せずに記録だけ残します。
  - 以後そのパスの読み込みは `this plugin crashed earlier (...); restart Brack to try it again` で失敗します。スキャンは失敗として記録して次のファイルへ進みます。キャッシュには成功だけを残すので、再起動後のスキャンで再び試されます。

### 自動保存（GUI、デバウンス）

- 定期保存ではなく、変更が 3 秒間止んだら保存します。変更が無ければ保存しません。
- 変更が止まずに続く場合（つまみを回し続ける、演奏中にパラメーターを報告し続けるプラグインなど）に備えて、最初の未保存の変更から 30 秒たったら、止むのを待たずに保存します（`kAutosaveMaxDelay`）。
- 保存に失敗したら、3 秒後にもう一度試します（毎フレームは試さない）。
- 変更の検出:
  - エンジンの `changeCount()`。ラックを変える公開メソッドと、プラグインからの通知（`PluginHostListener::pluginStateChanged`）で増えます。プラグインからの通知はオーディオスレッドから来ることもあるので、カウンターを増やすだけにしています。
  - CLAP では、出力イベントの `CLAP_EVENT_PARAM_VALUE` / `CLAP_EVENT_PARAM_GESTURE_END` も変更として数えます。CLAP の仕様ではエディタでの操作は出力イベントで知らせれば足り、JUCE 製の CLAP など、これしか送らないプラグインがあるためです。
  - GUI 自身の設定（追加フォルダ、セッションのパス、ウィンドウの位置と大きさなど）。
- MIDI は数えません。演奏中ずっと保存が走らないようにするためです。MIDI で変わったプラグインの状態や、何も知らせずに内部の状態を変えるプラグインの変更は、別の変更で保存するときか終了時まで保存されません。
- 保存はワーカースレッドで行い、エンジンへのほかの操作と順番に処理します。クラッシュしたプラグインは呼ばず、最後に保存できた状態を書きます。

### セッションのパスとラックを揃える

- GUI の Save は、ラックを開いた元のセッションファイルに書きます。そのため、覚えているパスとラックが食い違ってはいけません。
  - エンジンを変える前に、セッションを最後まで読みます（`parseSession`）。途中で壊れているセッション（型の違うプラグインやルートの項目）でも、ラックを空にした後で失敗することはありません。読み込みは、ラックを置き換えるか、失敗してラックに手を付けないかのどちらかです。
  - GUI は、覚えていたパスをラックと一緒にだけ戻します。ラックを復元しなかったとき（復元やコマンドラインのファイルを開くのに失敗したとき）は戻しません。
  - ラックを置き換えた後でエンジンを動かし直せなかった（デバイスが無い）読み込みは、成功とします。動かし直せなかったことはログに出し、エンジンは止めたままにします。失敗を返すと、Open が新しいラックに古いパスを残すためです。`brack_load_session` / `brack_load_session_json` も同じです。

## 12. DLL をほかのアプリに組み込むための機能

DLL の目標は、ほかのアプリが GUI と同じことを GUI なしでできることです。

### GUI と同じ機能（`test_api_parity`）

- エンジンの公開メソッドごとに、それを提供する C 関数か、提供しない理由を表に書きます。テストが `engine.h` と `brack.h` を読み、片方にだけ増えた関数や表に無い関数があれば失敗します。
- 今のところ提供しないのは `refreshSnapshot` だけです（キャッシュは 50 ms ごとに自動で更新されるため）。

### イベント（`Engine::pollEvent`）

- コールバックではなくキューにしました。アプリが自分のスレッドで取り出せるので、再入やスレッドの心配がありません。通知が要るアプリには、イベントが入るたびに呼ぶ関数（`setEventNotify`）があります。ホストスレッドから呼ぶので、中では自分のスレッドを起こすだけにしてもらいます。
- イベントはすべてホストスレッドで作ります。オーディオスレッドではメモリ確保もロックもしないためです。オーディオスレッドで起きたクラッシュも、アイドル処理（10 ms ごと）が `crashed()` を見て知らせます。
- 変更（`Changed`）はキューに 1 つまでにまとめます。つまみを回し続けると 10 ms ごとに変化するためです。何回変わったかは `changeCount` で分かります。
- キューは最新の 1024 件だけを持ちます。取り出さないアプリでメモリが増え続けないようにするためです。

### フレーム単位の MIDI（`sendMidiToPlugin` の `time`）

- 時刻の基準は、エンジン開始からの出力フレーム数（`renderPosition`）です。手動モードでは、アプリが `render` の前に読んだ位置がその呼び出しの先頭になるので、アプリ側で計算しやすくなります。
- MIDI キューのメッセージはそれぞれ時刻を持ちます。オーディオスレッドは処理ブロックごとに、ブロックの終わりより前のものだけを渡し、残りを `PendingMidi` に取っておきます。`PendingMidi` の領域は最初に確保し、あとからメモリを確保しません。
- ブロック内の位置は、各形式のイベントの時刻で渡します。CLAP はイベントが時刻順であることを求めるので、ブロックごとにイベントを安定ソートします（メモリ確保なし）。
- SRC を使う場合は、出力フレームと処理フレームを比率で換算します。全体が SRC の遅延の分だけ一様に遅れ、SRC が先読みしたブロックには間に合わないことがあります（最大 1 ブロック遅れる）。SRC を使わなければフレーム単位で正確です。
  - 出力が別のレートのデバイスに移ると、そこから比率が変わります。切り替えのたびに、そこまでに進んだ処理フレームから新しいレートで数えます（`FrameMap`）。エンジン開始からの位置全体に今の比率を掛けると、描画済みの分までずれ、鳴っていた音にノートオフが届かなくなります。
- **時刻の無いメッセージは、デバイスがあれば、届いた時刻から 1 周期後の、周期の中で届いた位置に置きます**（`ArrivalClock`）。メッセージを取り出すのは周期の頭だけなので、そのまま渡すと周期の中のどこで届いたかが失われ、最大 1 周期揺れます。キューには入れた時刻（steady_clock）か、ドライバーが付けた受信の時刻を記録し、オーディオスレッドが取り出すときに描画位置へ換算します。状態はオーディオスレッドだけが持つので、スレッドをまたぐ共有はありません。
  - 換算には、描画を始めるたびに「描画位置から steady_clock の進みを引いた値」を求め、直近の 2 つの窓（各 4 秒）でのその最大を使います。コールバックが遅れた回は値が小さくなるので、最大が遅れの無いときの時計になります。窓で区切るのは、デバイスの時計と steady_clock のずれに付いていくためです。
  - 値が止まったとみなす分（`stallNs`）より下がれば、デバイスが止まったものとして時計を求め直します。そこまで下がらなくても、時計より 1 ms 以上低い値が `stallNs` のあいだ続けば、デバイスがその分の時間を失ったものとして、その間の最大に下げます（遅れただけのコールバックなら、それまでに追いつく）。デバイスを開き直したときも（別のレートのデバイスへの切り替えを含む）、何も描画していない間に求め直します。
  - 遅れを 1 周期にするのは、周期の頭の直前に届いたものが次の周期に間に合うための最小だからです。SRC を使うときは、先読みの 1 ブロックを足します。
  - 時計は下がることがあります（窓の最大が古くなって抜けたとき、止まったとみなして求め直したとき、低い値が続いて下げたとき。後の 2 つでは、デバイスが失った時間の分だけ下がる）。そのまま置くと、後から届いたメッセージが、時刻を待っている前のメッセージより前に置かれます。ノートオフがノートオンより前に渡ると、音が鳴りっぱなしになります。そこで、前に置いたメッセージと同じかそれより後の瞬間のためのメッセージは、それより前に置きません。時計が下がった直後のメッセージは同じ位置にまとまり、順序が保たれます。先に送られた、より後の瞬間のためのメッセージは、それより前の瞬間のためのメッセージを引き留めません。守る順序はデバイスを開き直しても持ち越し（描画の位置は続いていて、前のデバイスのために置いたメッセージがまだ待っていることがあるため）、エンジンを始め直して位置が 0 に戻るときだけ忘れます（`forgetOrder`）。
  - 低い値が続いたときに下げるのは、x64 の PC の Bluetooth の出力（WASAPI）のためです。開いて 0.2〜0.6 秒のところで、コールバックの間が一度だけ約 11.5 ms 余計に空き、その後の値はずっと約 11.5 ms 低いままです。止まったとみなす時間（40 ms 以上）より短いので、求め直しでは拾えません。下げなければ、最初の窓の最大が抜ける 8 秒後まで、メッセージを約 11.5 ms 遅く置き、そこで一度に 11.5 ms 早めます。下げない実装では、`tools/midi-timing` の揺れの幅がこの段差のために 10〜12 ms ありました（段差の無い回は 0.03〜0.04 ms。15 章の「Windows（x64）」）。
    - 続く時間を `stallNs` にするのは、まとめて呼ぶサウンドサーバーでも最大の値が最長の間隔の 2 倍以内にまた来て、一時的に遅れたコールバックもそれまでに追いつくからです。1 ms は、落ち着いたときの値の揺れ（その出力で ±15 フレーム、0.3 ms）より大きくとりました。閾値を半周期にすると、周期 1920 フレーム（半周期 20 ms）では 11.5 ms の段差を拾えないので、周期によらない値にしました。
    - とらなかった案が 2 つあります。窓（4 秒）を短くすると、下がった時計には早く付いていけますが、まとめて呼ぶサウンドサーバー（VM の PulseAudio は 0.6 秒呼ばないことがある）では、まとまりの頭の最大を窓が取り逃がします。求め直す閾値（止まったとみなす分）を小さくすると、遅れただけのコールバック 1 回で時計が下がり、その間のメッセージが周期の頭に寄ります（最大を使う意味が無くなる）。下がり方ではなく下がったままの長さで見分けるのが、両方を崩さない形でした。
    - 時計が steady_clock から大きくずれる VM の音声デバイス（VMware Workstation の ES1371。実時間の約 95.5% で進む）でも、下げることで揺れの幅が 80〜84 ms から 23〜26 ms になりました（15 章の「MIDI の時刻の計測」）。下げなければ、ずれていく値の 8 秒前までの最大を持ち続けるためです。
  - アプリが自分で時計を推定して `time` を付けるより、デバイスのコールバックの時刻を直接見られるぶん情報がよく、別のレートへの切り替えもエンジンの中で同期的に分かります。MIDI ポートからの入力も同じ扱いです。
  - 手動モードでは実時間との対応が無い（オフラインの描画もある）ので、次の `render` の頭に置きます。
  - macOS（Apple シリコン、CoreAudio）での計測（`tools/midi-timing`）では、周期 480 フレームで、揺れの幅が 96 kHz で 4.9 ms から 0.044 ms に、192 kHz で 2.5 ms から 0.12 ms になりました。描画位置からの先行は平均で半周期です。Glosa が描画位置からデバイスの時計を推定して時刻を付けた送り方は、揺れの幅が 0.005〜0.011 ms で Brack より小さいものの、Brack はそれより 1.2〜2.5 ms 早く置きます。
  - 実機の x64 の PC の Bluetooth の出力では、揺れの幅は 0.017〜0.64 ms でした。VM では、揺れは VM の音声デバイスで決まっていました。OS ごとの値は 15 章の「Windows（ARM64）」「Windows（x64）」と、Linux の「MIDI の時刻の計測」にあります。
- **デバイスが止まったという判定は、コールバックの間隔に合わせます**（`CallbackCadence`）。デバイスのコールバックが「止まった」とみなす時間（`stallNs`）だけ来なければ、Brack は自分の時計で描画を続けます（デバイスが無くなった間も、プラグインと MIDI の時間を進めるため）。この時間を周期だけから決める（周期の 4 倍、少なくとも 40 ms）と足りません。サウンドサーバーは周期ごとに呼ぶとは限らないためです。PipeWire の quantum が 4096 なら、512 フレームのコールバックを 8 回続けて呼んだあと、85 ms 呼びません。そのたびに止まったと誤って判断して自分の時計で描画を始め、その間に来たデバイスのコールバックには無音を返します（VMware の Ubuntu 26.04 で、20 秒に 235 回）。`ArrivalClock` も、まとまりの頭で値が 1 まとまり分下がるたびに時計を求め直し、MIDI の位置が 74 ms 揺れます。
  - そこで、オーディオスレッドがコールバックの間隔を測り、直近の 2 つの窓（各 4 秒）での最長の間隔の 2 倍を、止まったとみなす時間の下限にもします。250 ms 以上の間隔は本当に止まったものとして数えないので、止まって戻ったデバイスを「それほどまれにしか呼ばない」とは覚えません。長い間隔は、来なくなってから 2 つの窓（8 秒）で忘れます。デバイスを開き直したときも忘れます。VMware の Ubuntu 26.04（PulseAudio）の周期 512 フレームでは、20 秒に 26 回あった誤判定が 0 回になりました。
  - 最初の長い間隔は、まだ覚えていないので、一度だけ止まったと判断することがあります。
  - `ArrivalClock` は、止まったとみなす時間を描画のたびに受け取り、自分の時計で描画するスレッドも毎回読み直します。デバイスを開いたときに決めた値を持ち続けると、まとめて呼ぶデバイスに付いていけないためです。
- **デバイスモードでは、時刻を実時間（Brack の時計）でも指定できます**（`sendMidiToPluginAtTime`、`brack_send_midi_at_time`）。デバイスの時計を持つのは Brack なので、アプリが描画位置で指定するには、外からデバイスの時計を推定するしかありません（Glosa はそうしていて、レートの違うデバイスへの切り替えで時計がずれました）。実時間の指定は、届いた時刻の代わりにその時刻をキューに記録するだけで、時刻の無いメッセージと同じ道を通ります。その時刻に `brack_send_midi` で送ったのと同じ位置に置かれるので、先に送っておけば、アプリのスレッドの揺れが入りません。
  - 時計は Brack が `brack_now_ns()` で出します。アプリの時計（.NET の Stopwatch など）と steady_clock が同じとは限らないためです。macOS では、steady_clock はスリープの時間を含む `mach_continuous_time` と同じ値でした。CoreMIDI のホスト時刻（`mach_absolute_time`）はスリープの時間を含まないので、計測した Mac では 14 万秒ずれていました。
  - 手動モードでは、アプリの `render` の呼び出しが時計なので、実時間で指定したものも時刻の無いメッセージと同じく次の `render` の頭に置きます。時刻を指定するなら、アプリにとって推定の要らない描画位置（`brack_send_midi_at`）を使います。
  - 先に送ったメッセージは時刻まで `PendingMidi` に入っているので、何秒も先のものを大量に送ると溢れます。
  - 過ぎた時刻のメッセージは、すぐに置きます（`brack_send_midi` と同じ）。macOS で時刻を付けて 20 ms 先に送ると、揺れの幅は 0.027 ms で、その時刻に送ったのと同じ位置に置かれました。
- **MIDI ポートからの入力は、ドライバーが付けた受信の時刻で置きます**（`MidiReceiveFn` の `whenNs`）。Brack の受信スレッドに届くまでの揺れが入りません。
  - CoreMIDI は、パケットのホスト時刻にスリープの時間（`mach_continuous_time` との差）を足して steady_clock に直します。時刻の無いパケット（0）は、受け取ったときの時刻にします。CoreMIDI は、仮想ソースに未来の時刻を付けて送られたパケットをその時刻まで待ってから渡すので、先読みの送信は受け取ったときの時刻でも時刻どおりに鳴ります。ドライバーの時刻で置いて減るのは揺れです。`tools/midi-timing` の `midi`（MacBook の 96 kHz）では、揺れの幅が 0.116 ms から 0.032 ms になり、API から直接送ったとき（0.036 ms）と同じ水準になりました。
  - Windows MIDI Services（Brack の仮想ポート）は、メッセージの時刻（QPC）をナノ秒にして渡します。MSVC の steady_clock は QPC そのもの（同じ原点、同じ割り算）なので、そのまま Brack の時計になります。WinMM は、受け取ったときの時刻のままです。`midiInProc` の時刻はミリ秒に切り捨てられ、受け取ったときの時刻より揺れが大きかったためです（15 章の「MIDI 入力の時刻（WinMM）」）。
  - Linux（ALSA）は、シーケンサーがキューの実時間で付けた届いた時刻を steady_clock に直して渡します（15 章の「MIDI ポート」）。

### エディタの埋め込み（`showPluginGuiIn`）

- エディタのウィンドウ（`HostWindow`）を、アプリのウィンドウの子（`WS_CHILD`、枠なし、左上）として作れます。大きさが変わるたびに `EditorResized` で知らせます。
- 子ウィンドウは Brack のホストスレッドが作り、親はアプリのスレッドにあります。スレッドをまたぐ親子関係では、片方がもう一方へ同期メッセージを送ることがあり、両方が相手を待つとデッドロックします。対策は 2 つです。
  - `WS_EX_NOPARENTNOTIFY` で、作成時に親へ送る `WM_PARENTNOTIFY` を止めます。
  - `HostThread::invoke` は、ホストスレッドの処理を待つ間も、他スレッドから送られてきたメッセージに応答します（`MsgWaitForMultipleObjectsEx` と `PM_QS_SENDMESSAGE`）。アプリの UI スレッドが Brack を呼んで待っている間に、ホストスレッドがアプリのウィンドウへ送っても止まりません。
- Windows では、子ウィンドウの DPI 対応の種類が親と同じでなければなりません。エディタを作る間だけ、ホストスレッドの DPI 対応を親ウィンドウに合わせます（`ParentDpiScope`）。プラグインがその中で作る子ウィンドウも合います。
- 親ウィンドウごと破棄された場合は、`WM_DESTROY` を受けてエディタを閉じます。ただ、そのときプラグインのウィンドウはもう消えているので、親ウィンドウより先にエディタを閉じてもらうよう説明しています。
- 自分のウィンドウしか開けない CLAP プラグイン（floating のみ）は埋め込めないので、エラーにします。

### 構造体の大きさ（`struct_size`）

- `brack_config` と `brack_event` は、後ろにだけ項目を足して大きくなります。呼ぶ側は、自分のヘッダーでの大きさを `struct_size` に入れます。
- brack.dll は、その大きさと自分の知る大きさの小さいほうだけを読み書きし、呼ぶ側の構造体に無い項目は既定値にします。最初の形より小さければ拒みます。これで、新しいヘッダーで作ったアプリが古い brack.dll を、古いヘッダーで作ったアプリが新しい brack.dll を使えます。
- `brack_config_init` は、ヘッダーの中のインライン関数にしました。brack.dll の関数にすると brack.dll の大きさで書き込むので、古いヘッダーで作ったアプリの構造体からはみ出すためです。

### スキャン

- スキャンはエンジンの状態を使わないので、静的関数にして、呼んだスレッドで動かします。ホストスレッドで動かすと、スキャン中はほかの操作が止まります。
- キャッシュファイルを指定できます（GUI と同じ仕組み）。テストやアプリ専用のフォルダのために、標準の場所を探さない指定もできます。

### .NET バインディング（`bindings/dotnet/`）

- **2 層構成**。
  - `Native/NativeMethods.cs` は、C API を名前も引数もそのまま宣言する層です。`test_api_parity` が `brack.h` と突き合わせ、片方にしか無い関数があれば失敗します。
  - `BrackEngine` / `BrackLibrary` が、その上の C# らしい層です。
- **`LibraryImport`（ソース生成）を使います**。実行時のマーシャリングコード生成が要らず、AOT とトリミングに対応します（`IsAotCompatible`）。JSON も `System.Text.Json` のソース生成で読みます。すべての関数に `cdecl` を指定しています。x64 では意味がありませんが、x86 では C 側の `BRACK_CALL` と一致させる必要があるためです。
- **エンジンのハンドルは `SafeHandle`** です。`Dispose` し忘れても、ファイナライザーで `brack_engine_destroy` されます。
- **コールバック**（ログ、イベント通知）は `UnmanagedCallersOnly` の静的メソッドで受け、`GCHandle` でエンジンに戻します。ハンドルは弱参照にして、通知のためにエンジンが回収されなくなるのを避けています。ハンドラーの例外は握りつぶします。ネイティブ側に巻き戻すとプロセスが落ちるためです。
- **音声・MIDI のスレッドから呼ぶもの**（`Render`、`SendMidi` 系）は、ヒープを確保しません。`SendMidi` 系は失敗を例外ではなく `MidiSendResult` で返します。`Render` が例外を投げるのは、配列が `frames` より短いときだけです。ネイティブ側が配列の外に書き込まないためです。チャンネルごとの配列は、スタック上の `GCHandle` で固定してから渡します。ID の文字列は、短ければスタック上で UTF-8 に変換されます（`LibraryImport` の既定）。
- **失敗は `BrackException`** にしました。`brack_last_error()` はスレッドごとで、次の呼び出しで上書きされるので、失敗した直後に同じスレッドで読みます。
- **バッファの大きさ**。テキストを返す関数は、まず十分な大きさのバッファ（スキャンは 256 KB、ほかは 16 KB）で呼び、足りなければ報告された大きさで呼び直します。空のバッファで大きさを問い合わせてから呼ぶと、キャッシュを渡さないスキャン（`brack_scan_plugins`）は、すべてのプラグインファイルを 2 回読み込むためです。キャッシュを渡せば、2 回目は 1 回目が書いたキャッシュから読むので、重いのは 1 回目だけです。
- **対象は .NET 10 だけ**です。.NET 10 は LTS で、.NET 8 のサポートは 2026 年 11 月に終わります。.NET 8 の参照パックがあれば、`TargetFrameworks` に足すだけで対応できます。
- **アセンブリの名前とパッケージ ID は `Brack.NET`** です。ランタイムを指定して publish すると、パッケージのネイティブの brack.dll がマネージドのアセンブリの隣に置かれます。Windows のファイル名は大文字と小文字を区別しないので、`Brack.dll` では 2 つがぶつかり、パッケージを使うアプリの publish が NETSDK1152 で失敗します。名前空間は `Brack` のままです。
- **brack.dll（Linux では libbrack.so）の置き場所と読み込み**（`Native/NativeLibraryResolver.cs`）。
  - NuGet パッケージでは `runtimes/win-x64|win-x86|win-arm64/native/`、`runtimes/linux-x64|linux-arm64/native/`、`runtimes/osx-arm64|osx-x64/native/` に入れ、.NET が実行中の OS とアーキテクチャに合うものを選びます。.NET に 32 ビットの x86 の Linux は無いので、`linux-x86` はありません。
  - プロジェクト参照でも、同じ場所（参照する側の出力の下）にコピーします。ただし .NET がそこを探すのは NuGet のパッケージ（deps.json に書かれたもの）だけなので、バインディング自身のリゾルバーが、実行中の OS とアーキテクチャの `runtimes/<rid>/native/brack.dll`（`libbrack.so`）を読み込みます。出力のすぐ下に 1 つだけ置く方法では、AnyCPU のアプリが x86 で動いたときに読めないため、この方法にしました。
  - プラグインホストは libbrack.so の隣に入れます。パッケージ（zip）には実行の許可が残りませんが、NuGet が展開するときに付けます（VMware の Ubuntu 24.04 で確かめた）。
  - 探す順番は、`LoadNativeLibrary` で指定したもの、`runtimes/<rid>/native/`、.NET の通常の探索（アプリのフォルダなど）です。リゾルバーは `NativeMethods` の静的コンストラクタで登録するので、最初の呼び出しより前に必ず登録されます。
- **テストはテストフレームワークを使わない**コンソールアプリにしました。NuGet から何も取得せずに動き、ctest からほかのテストと同じく引数（brack.dll とテスト用シンセ）で起動できるためです。.NET SDK の `dotnet` は 64 ビットなので、ctest に登録するのは 64 ビット版のビルドだけです（Windows と Linux）。
  - Unix の .NET は環境変数を自分の中に持ち、`Environment.SetEnvironmentVariable` は C ライブラリの環境を変えません。テスト用シンセのログの場所はプラグインホストに受け継がせるものなので、Linux では `setenv` も呼びます。

## 13. 他プラットフォームへの対応

Windows（x64・x86）以外の OS とアーキテクチャへの対応です。「実装したこと」は、OS ごとの部分のうち、実機が無くても正しさを確かめられるものです。今の状態は「アーキテクチャごとの状態」の表に、残りの作業は TODO の表にあります。OS ごとの実装の判断は 15 章にあります。

### 実装したこと

- **プラグインファイルの規則**（`plugin/plugin_files.*`）。形式ごと・OS ごとに違う次のことを 1 か所の表にしました。OS を引数で受けるので、3 つの OS すべての規則を Windows 上のテスト（`test_portable`）で確かめられます。
  - 拡張子。VST2 は Windows では `.dll`、macOS では `.vst`（バンドル）、Linux では `.so` です。
  - バンドルかどうか。VST3 はどこでもバンドルで、macOS では CLAP と VST2 もバンドルです。
  - バンドル内の実行ファイルの場所と、別アーキテクチャ用のバンドルの見分け方。
  - 読み込み（CLAP・VST2・VST3）、スキャン、形式の判定は、すべてこの表を通します。
- **VST3 のモジュールの入口と出口**。Windows は `InitDll` / `ExitDll`（無くてもよい）、Linux は `ModuleEntry(ライブラリのハンドル)` / `ModuleExit`（必須）、macOS は `bundleEntry` / `bundleExit` です（15 章の「macOS」）。
- **UTF-16 の変換**（`utf16ToUtf8` / `utf8ToUtf16`）。VST3 の文字列はどの OS でも UTF-16 ですが、`wchar_t` は Windows 以外では 32 ビットなので、`wchar_t` を経由せずに変換します。
- **エディタのウィンドウの種類**（`HostWindow::api()`）。CLAP と VST3 に渡すウィンドウの種類を、`HostWindow` の種類（Win32 / Cocoa / X11）から選びます。CLAP のエディタのコード（`clap/clap_editor.cpp`）は OS に依存しません。
- **OS ごとのファイルの分離**。`plugin/library.cpp` の Windows 専用部分（SEH による封じ込め、落ちた場所の特定）は `library_win32.cpp` にあります。`library_posix.cpp` は、落ちた場所を `dladdr` で特定し、封じ込めをシグナルで行います（11 章）。PE の検査は、ELF・Mach-O と一緒に OS によらないコードにあります（下記）。
- **その他**。
  - CLI は、Windows 以外では `SIGINT` / `SIGTERM` で終了処理に入ります。
  - GUI は、macOS（ヒラギノ）と Linux（Noto CJK）の日本語フォントを探します。
  - vst2sdk の `vst.h` が使う `__cdecl` は、Windows 以外では空にします（CMake）。
- **バイナリの検査**（`plugin/binary_info.cpp`）。PE・ELF・Mach-O（1 つのアーキテクチャのものも、ユニバーサルも）を、どの OS でも読みます。
  - アーキテクチャは、PE のマシン種別、ELF の `e_machine`、Mach-O の CPU の種類から、x64・x86・arm64 の名前にします。ユニバーサルなものは、入っているすべてのアーキテクチャを持ち、Brack と同じものがあればそれで動かします。
  - エクスポートは、PE のエクスポート表、ELF の `.dynsym`、Mach-O のエクスポートのトライ（無い古いものは `LC_SYMTAB`）から読みます。ユニバーサルなものは、Brack が読み込むアーキテクチャのものから読みます。トライから読む理由と実物での確かめは、15 章の「アーキテクチャ」にあります。
  - macOS のバンドルのアーキテクチャは、フォルダではなく実行ファイルのヘッダーで決めます（`pluginArchitecture`）。
- **ビルドのアーキテクチャ**（CMake の `BRACK_ARCH`）。MSVC のアーキテクチャ ID、macOS の `CMAKE_OSX_ARCHITECTURES`、それ以外は `CMAKE_SYSTEM_PROCESSOR` から、x64・x86・arm64 を決めます。64 ビットの PC で `-m32` を付けたビルドは x86 にします。それ以外はエラーにします。
- **VST3 の ARM64 のフォルダ**。Windows の ARM64 版が探すのは `arm64x-win`、`arm64-win` です。`arm64ec-win` は探しません。ARM64EC のコードは ARM64 のプロセスには読み込めないためです。
- **確かめ方**。`tools/linux_syntax_check.sh` で、Windows 専用と macOS 専用のファイル以外を、x64・x86・arm64 のそれぞれに向けた Linux の g++（`-Wall -Wextra`）で、構文だけコンパイルします。
  - プラグインホストとの共有メモリ（`ControlBlock`）の `uint64_t` は、8 バイト境界を明示します。32 ビットの x86 の Linux では構造体の中の `uint64_t` を 4 バイト境界に置くので、明示しないと大きさがほかと違い、x86 のプラグインホストと 64 ビットの Brack の通信が壊れます。この違いは、大きさの `static_assert` が見つけます。

## 14. それ以前の判断（エンジン、MIDI 入力、出力デバイス、マスターボリューム、GUI）

### MIDI 入力の再接続（WinMM）

- MIDI プレイヤーを再起動するとデータが届かなくなる件への対策です。ドライバーが接続を閉じた通知（`MIM_CLOSE`）を記録し、約 1 秒ごとの確認で切断を検出します。失敗したハードウェア入力は、ポートが再び列挙されたら静かに開き直します。
- 仮想ポートは自動で作り直しません。MidiSrv の不具合（microsoft/MIDI#1047、9 章）があるので、作成と削除の回数を増やさないためです。
- 壊れた SysEx（`MIM_LONGERROR`）で返されたバッファも、ドライバーへ返し直します。返さないと、エラーが続いたときにバッファが尽きます。
- デバイスが消えた後は `midiInClose` が失敗することがあります（microsoft/MIDI#1157）。その場合はドライバーがまだバッファに書く可能性があるので、解放せずに残します。閉じ始めた後の受信データはアプリへ渡しません。

### エンジンのスレッドとロック

- オーディオスレッドはロックを取りません。
- ルーティンググラフは、ホストスレッドで作り直してアトミックに差し替えます。古いグラフは、オーディオスレッドがその回の描画を終えたのを確かめてから破棄します。2 秒たっても終わらなければ、破棄せずに漏らします。
- MIDI キュー（`util/midi_queue.h`）は、書き込みが複数・読み出しが 1 つのリングバッファです。書き込み側（MIDI ドライバーのスレッド、API の呼び出し）どうしはミューテックスで直列化し、読み出し側（オーディオスレッド）は待ちません。領域は最初に確保し、以後メモリを確保しません。満杯なら、そのメッセージを捨てて数えます。

### 出力デバイス

- **代わりの時計。** デバイスのコールバックが来なくなることがあります。デバイスが消えると（抜いた、ドライバーのリセット）miniaudio はストリームを止め、戻ると再開します。サウンドサーバーや VM の音声デバイスが止まったときも、コールバックは来ません。何もしなければ、その間プラグインの時間が止まり、MIDI がキューにたまり、戻ったときにまとめて処理されます。どの OS でも同じ扱いです。
  - そこで、デバイスモードでは代わりの時計のスレッドがコールバックを見張ります。止まったとみなす時間（`stallNs`、12 章）を過ぎても来なければ、実時間どおりに自分で描画し、出力を捨てます。コールバックが戻れば、すぐに退きます。
  - デバイスのコールバックと代わりの時計が同時に描画することはありません。描画の途中にコールバックが来たら、そのコールバックは 1 バッファ分の無音を返します。
  - スリープの後のような長い空白は、最大 1 秒分だけ描画して追いつきます。
  - 代わりの時計で動いている間は、状態の JSON の `deviceStalled` が真になり、GUI にも表示します。
- **開き直しの失敗。** 失敗し続ける間は代わりの時計のまま、時間を途切れさせずに試し続けます。失敗のログは最初の 1 回だけ出します。
- **miniaudio のコンテキストは破棄しません。** 関数内の静的変数にすると、プロセスの終了時に brack.dll の静的デストラクタが破棄します。Windows では、その時点で WASAPI のコマンドスレッドがもう無いので、`ma_context_uninit()` が返事を待ち続け、brack.dll を使うプロセスが終われません。破棄しなくても、プロセスが終われば OS が回収します。

### マスターボリューム

- SRC の後で全出力チャンネルにかけます。値が変わると、そのバッファの中で直線的に移行します。
- メーターはゲインをかけた後の値を表示します。
- セッションには `masterGain` として保存します。
- どのスレッドからでも呼べ、待ちません。値は次のバッファから効きます。

### GUI

- 画面は左のメニューで Rack、Routing、Audio settings、Log に切り替えます。Rack では音源ごとに、つながっている MIDI 入力と出力先を表示だけし、ルートごとのゲインを変えます。ルートをつなぎ替えるのは Routing です。音源 1 つに関わることを 1 か所で見られるようにするためです。
- 部品は ImGui の標準のウィジェットと、`ImDrawList` で描く自作の部品（`src/gui/widgets.cpp`）で作ります。文字はシステムのフォントです。日本語のデバイス名やポート名を表示するためです。
- 配置は固定で、窓の幅に下限があります。ImGui には折り返して並べる仕組みが無いためです。
- MIDI ルーティング表は、行をプラグインのノートポート、列を MIDI 入力にしています。列の見出しは 90 度回して、列を狭く保ちます。
- ImGui のテーブルは列をラベルの ID で照合するので、列 ID に位置を表す接尾辞を付けます。付けないと、入力を並べ替えたときに列が追従しません。
- エンジンへの操作は GUI のワーカースレッドで順に行い、結果を UI スレッドへ戻します。画面はスナップショット（`cachedSnapshot`）を待たずに読みます。スナップショットは、エンジンが約 50 ms ごとと、求められたときにホストスレッドで作り置きます。メーター、CPU 負荷、デバイスが止まった印は、その場で読みます。
  - プラグインの初期化と活性化はホストスレッド（CLAP のメインスレッド）で行い、数秒かかることがあります。GUI がスナップショットや操作の結果をホストスレッドで待つと、プラグインやセッションの読み込み中に窓が固まります。
  - 操作が残っている間は、回る印と今の作業名を出します。窓を閉じるときは、残った操作が終わるのを待ってから設定を保存します。
  - DLL と CLI は同期のままです（DLL には待たない `brack_get_status_cached` があります）。
- プラグインの表示名はミューテックスで守ります。名前の変更中に、プラグインがオーディオスレッドからログを出す（ログには表示名が付く）ことがあるためです。
- ゲインのフェーダーで操作した値は、エンジンのスナップショットが追いつくまで UI 側で保持します。保持しないと、変更が反映されるまでつまみが元の位置に戻ります。
- ゲインのフェーダーはダブルクリックで 0 dB に戻ります。

## 15. プラグインホストプロセス（`src/core/remote/`、`src/host/`）

プラグインは既定で 1 つずつ、Brack とは別のプロセス `brack-host-<アーキテクチャ>`（Windows では `.exe`）で動きます。目的は 2 つです。

- 11 章の封じ込めでは捕まえられない終わり方（プラグインが自分で作ったスレッドやウィンドウ処理の中でのクラッシュ、`__fastfail`、`abort()`、止まったままの処理）でも、Brack を落とさないこと
- Brack と違うアーキテクチャのプラグインを動かすこと

「通信」「終わり方の扱い」「起動」「確かめたこと」に出てくる OS の仕組み（名前付きパイプ、イベント、ハンドルの引き継ぎ、ジョブ、`__fastfail`、MMCSS など）は Windows のものです。Linux と macOS でそれに当たるものは、下の「Linux」と「macOS」にあります。

### 境目（`HostedPlugin`）

- エンジンがプラグインについて使うメソッドを、抽象クラス `HostedPlugin`（`plugin/plugin.h`）にしています。
  - 実装は、同じプロセスの `PluginInstance`（形式ごとの実装の基底）と、プラグインホストの代理 `RemotePlugin` です。
  - エンジンは、どちらで動いているかを `separateProcess()` でしか区別しません。
  - 代理を `PluginInstance` の派生にしなかったのは、`callPlugin` や形式のフックなど、代理には意味の無いものを持たせないためです。
- **音声処理を 2 段階にしました**（`beginProcess` / `endProcess`）。`processBlock` は、全プラグインに処理を頼んでから、1 つずつ結果を待ってミックスします。
  - グラフは楽器を並べてミックスするだけで、プラグインどうしの直列のつながりはありません。そのため、別プロセスのプラグインは並列に動きます。
  - 同じプロセスのプラグインは `endProcess` で処理するので、順に動きます。

### 通信（`remote/host_protocol.h`）

- **パイプ。** 名前付きパイプで、CBOR（nlohmann/json の `to_cbor`）のメッセージに長さを付けて送ります。依存ライブラリは増えず、状態のバイナリもそのまま運べます。
  - Brack が要求を送り、返事を待ちます。プラグインホストは、ログや通知（エディタが閉じた、再起動の要求など）を「note」としていつでも送ります。Brack は、返事を待つ間とアイドル処理（10 ms ごと）で note を読みます。
  - プラグインホストからは要求を出しません。そのため、互いに相手を待ってデッドロックすることはありません。
  - 両端とも overlapped I/O です。同期 I/O では同じハンドルの読み込みと書き込みが直列になり、プラグインホストが要求を待つ間に note を書けなくなるためです。
- **制御ブロック。** Brack がプロセスの起動時に作る共有メモリです。1 ブロック分の MIDI（イベント 4096 個、SysEx 256 KB）、結果、状態の変更の回数、クラッシュの記録が入ります。
  - レイアウトは固定幅の整数だけで作り、32 ビットと 64 ビットで同じ大きさになることを `static_assert` で確かめています。
- **出力。** プラグインホストが活性化のたびに作る共有メモリです。チャンネル数は活性化するまで分からないので、プラグインホストの側で作ります。Brack はハンドルを `DuplicateHandle` で自分のプロセスに複製して開きます。
- **合図。** 自動リセットのイベント 2 つ（「処理して」と「済んだ」）です。Brack の音声スレッドは「済んだ」とプロセスのハンドルを一緒に待つので、プラグインホストが消えればすぐに分かります。
- **状態の変更の知らせ。** プラグインはオーディオスレッドからも知らせてくるので、制御ブロックの回数を `std::atomic_ref` で増やします。Brack は、ブロックごと、要求ごと、アイドル処理ごとに回数を比べます。メッセージで送る方式は採りませんでした。処理の直後に変更が数えられていること（`test_crash` が求める）を満たせないためです。
- **MIDI。** Brack 側は生の MIDI のまま渡し、形式ごとの変換はプラグインホスト側で行います。
- **バージョン。** プロトコルのバージョン（`kProtocolVersion`）をコマンドラインで渡し、メッセージか共有メモリの形を変えるたびに上げます。違えばプラグインホストは終了コード 101 で終わり、Brack は「ビルドの違うプラグインホスト」と報告します。

### 終わり方の扱い

- **プラグインホストでの記録。** 次の 3 つの経路で、制御ブロックに報告を書いてから自分を `TerminateProcess` で終えます。その後プラグインは呼びません（解放もしません）。
  - `callPlugin` が捕まえたクラッシュ
  - 未処理例外フィルター（自分のスレッドやウィンドウ処理の中のクラッシュ）
  - 要求の処理の後とアイドル処理での crashed の確認
- **報告にならない終わり方。** `__fastfail` はフィルターを通らないので、Brack が終了コードから報告します（`crashed: fast fail (0xC0000409)`）。テスト用シンセの `abort()` も、静的 CRT が `__fastfail` で終えるので同じ報告になります。
- **止まったまま。** 音声処理は 2 秒、要求は種類ごとの時間（生成と状態は 60 秒、エディタと活性化は 30 秒、そのほかは 10 秒）で打ち切ります。プロセスを終わらせ、`stopped responding in <処理>` と報告します。
  - 音声処理の 2 秒は、エンジンが音声スレッドを待つほかの箇所（2 秒）に合わせました。
  - 遅いプラグインだけを無音にして先へ進む方法は採らず、全体で待ちます。オフラインの書き出しで毎回同じ結果になるからです（利用者と決めた方針）。
- **Brack 側の状態。** `RemotePlugin` は終わり方を `None` / `Ended` / `Hung` の 1 つの値で持ちます。
  - 音声スレッドから変えることもあるので、そこではメモリを確保せず、値と処理名（文字列リテラル）を書くだけにしています。報告の文字列は、ホストスレッドで初めて求められたときに作ります。
  - 落ちた後の `saveState` は、最後に保存または読み込んだ状態を返します。`reloadPlugin` は、その状態で新しいプロセスに読み込み直します。
- **Brack が落ちたとき。** すべてのプラグインホストを、`KILL_ON_JOB_CLOSE` と `DIE_ON_UNHANDLED_EXCEPTION` のジョブに入れます。Brack が強制終了されても残りません。エラー報告のダイアログも出しません（`WerSetFlags`、`SetErrorMode`）。
- **クラッシュのログ。** `Engine::checkEvents` で出します。どちらで動いていたかによって、「再起動して」と「読み込み直して」を出し分けるためです。

### 起動

- **実行ファイルの場所。** brack.exe・brack-cli.exe・brack.dll のうち、このコードを含むモジュールと同じフォルダから探します。.NET のパッケージでも、brack.dll と同じ `runtimes/<rid>/native/` に入れています。Linux と macOS では、隣に無ければインストールの `../libexec/brack` も探します（下の「Linux」の「場所」）。
- **引き継ぐハンドル。** `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` で 4 つ（パイプ、制御ブロック、イベント 2 つ）に限ります。Brack 側は、パイプのもう一方の端を起動の直後に閉じます。プラグインホストが消えればパイプが切れるようにするためです。
- **一斉に読み込む。** セッションのプラグインは、作って状態を読み込むところまでを一斉に行い（`Engine::makePlugin`）、その後セッションの順にラックに入れます（`Engine::installPlugin`、ホストスレッド）。プラグインホストの起動、`create`、状態の読み込みを 1 つずつホストスレッドで待つと、読み込みに時間のかかるプラグイン（サンプルの読み込み、ライセンスの確認）の分がそのまま足し算になるためです。
  - プラグインホストのプラグインは、プラグインホストとのやり取りだけで作れるので、どのスレッドからでも作れます。作業用のスレッドの数は、プラグインの数と CPU の数（4 以上）の少ないほうです。同じプロセスのプラグインは、ホストスレッドで 1 つずつ作ります。`loadSessionJson` をホストスレッドから呼んだときは、作業用のスレッドを使いません（作業用のスレッドがホストスレッドを待つため）。
  - `addPlugin` でも、プラグインホストのプラグインは呼んだスレッドで作ります。読み込みの間も、ホストスレッドはほかのプラグインのエディタやアイドル処理を続けます。
  - 失敗したプラグインは、その位置に空のスロットとして残します。
- **一斉に活性化する。** エンジンを動かすとき（`startRunning`）の活性化も、プラグインホストのプラグインは一斉に行います（`Engine::activateSlots`）。同じプロセスのプラグインは、その間にホストスレッドで 1 つずつ活性化します。作業用のスレッドはホストスレッドに何も頼みません（ホストスレッドは作業の終わりを待っているため）。
  - 状態の読み込みか活性化に 1 秒かかるテスト用シンセを 4 つ入れると、どちらも 1.0〜1.2 秒で済みます（1 つずつなら 4.0〜4.2 秒。`test_isolation`）。
  - 1 つずつのままなのは、破棄（`clear`、終了時）と、プラグインが求めた再起動（`onIdle`）です。
- **1 つずつ読み込む設定。** `loadPluginsSerially` をオンにすると、セッションの読み込みと活性化を 1 つずつ行います。2 つ同時に起動すると失敗するプラグインがあるためです。SOUND Canvas VA を 2 つ同時に読み込むと、2 つ目が「Parameter file1 read error」のダイアログを出して閉じるまで止まるか、状態の読み込み（`effSetChunk`）でアクセス違反を起こします。1 つずつなら毎回読み込めます。既定は並列です。どのプラグインが同時の起動に弱いかを、Brack からは知る手段がないためです。
- **カレントディレクトリ。** Brack と同じにします。プラグインのパスは絶対パスにして渡し、記録には渡されたとおりのパスを残します。プラグインホストのフォルダで起動すると、相対パスのプラグインが読み込めないためです。
- **前面に出る権利。** エディタを開く前に `AllowSetForegroundWindow` を呼び、プラグインホストがウィンドウを前面に出せるようにします。
- **埋め込み。** アプリのウィンドウの子にするエディタ（12 章）は、プロセスをまたぐ親子になりますが、そのままで動きます（`test_dll`）。ただし Windows はプロセスをまたぐ親子の入力キューをつなぐので、プラグインホストの GUI スレッドが止まると、アプリの UI も止まることがあります（未確認）。
- **オーディオスレッドの優先度**（`util/realtime_win32.cpp`）。
  - Brack の再生スレッドとプラグインホストのオーディオスレッドを、MMCSS の「Pro Audio」タスクに入れます。優先度はリアルタイムの範囲（16〜31）になります。
  - 再生スレッドは miniaudio に入れさせます（`config.wasapi.usage`）。設定しなければ、再生スレッドは miniaudio の既定の `THREAD_PRIORITY_HIGHEST`（優先度 10）で動きます。
  - プラグインホストは、オーディオスレッドの最初のブロックで自分で入れ、結果を Brack に知らせます。
  - 結果は Brack がログに出します。Linux と同じく、同じ結果は 1 度だけです。再生スレッドが入れたかどうかは miniaudio が残すハンドル（`hAvrtHandle`）で分かりますが、失敗の理由は残らないので、ログには「入れなかった」とだけ出ます。
  - 優先度は、プラグインホストのスレッド（`test_isolation`、x64 と x86）も、`brack-cli play` の再生スレッド（設定の前は 11）も 24 になりました。

### アーキテクチャ

- **プラグインのアーキテクチャ。** 読み込む前に `pluginArchitecture()` で調べます。Windows と Linux の VST3 バンドルは、アーキテクチャごとのフォルダのどれに実行ファイルがあるかで決めます（Brack と同じものを優先）。それ以外（単体のファイルと macOS のバンドル）は、実行ファイルのヘッダー（PE・ELF・Mach-O。`inspectBinary`、13 章）から読みます。ユニバーサルなものは、Brack と同じアーキテクチャが入っていればそれにします。
- **アーキテクチャの違うプラグイン。** `pluginsInProcess` でも、そのアーキテクチャのプラグインホストで動かします。
- **バイナリの検査の実物での確かめ。** `inspectBinary` が読むアーキテクチャとエクスポートは、ELF では、Debian 13 のパッケージ（zam-plugins と dragonfly-reverb の VST2・VST3・CLAP）の arm64・x64・x86 の計 330 ファイル（どれも `strip` 済み）で、`file` と `nm -D --defined-only` の答えとすべて一致しました。Mach-O でも、システムやアプリのバンドルなどの計 62 ファイル（ユニバーサル、arm64、arm64e、x64 だけのもの）で、アーキテクチャごとの `dyld_info -exports` の答えとすべて一致しました。
  - Debian の VST2 は `VSTPluginMain` を出さず `main` だけを出すので、Brack は `main` も探します。
  - `strip -u -r` などでシンボル表から外部のシンボルを消した Mach-O も、dyld はエクスポートのトライから引くので読み込めます。そのため Brack はトライから読み、トライの無い古いもの（macOS 10.6 より前）だけシンボル表から読みます。シンボル表しか読まないと、そうした VST2 のバンドルをスキャンで飛ばします。
  - arm64e。macOS のシステムのものは arm64e で、CPU の種類が arm64 と同じなので、Brack は arm64 と読みます。arm64 のプロセスが arm64e だけのバンドルを `dlopen` して呼べることを確かめたので、これで正しいです。
  - 32 ビットの x86 の Mach-O は、実物が手元に無く、今の Xcode では作れないので、確かめていません。Brack は macOS で x86 のプラグインを動かさないので、アーキテクチャの名前が読めれば足ります（見本では確かめています）。
- **ビルド。** CMake は 1 つのビルドで 1 つのアーキテクチャしか作れません。そこで、同梱するプラグインホストを、ほかのビルドの `bin`（`BRACK_OTHER_ARCH_BINS`。既定は `build`・`build-x86`・`build-arm64` のうち自分以外）から、ビルドのたびに自分の `bin` にコピーします（`cmake/copy_plugin_hosts.cmake`）。ExternalProject でまとめて作る案もありましたが、利用者と相談してこちらにしました。
- **同梱するプラグインホスト**（`BRACK_BUNDLED_HOSTS`）。利用者が決めた次の表のとおりです。

  | Brack | 同梱するプラグインホスト |
  |---|---|
  | Windows x64 版 | x86、x64 |
  | Windows 11 ARM64 版 | x86、x64、ARM64 |
  | macOS Intel 版 | x64 |
  | macOS Apple Silicon 版 | x64、ARM64 |
  | Linux x64 版 | x86、x64 |
  | Linux x86 版 | x86 |
  | Linux ARM64 版 | x86、x64（FEX-Emu）、ARM64 |

  - x86 版（Windows）は x64 版と同じです。表に無いものは `bin` から消します。`cmake --install` の配布物と、.NET のパッケージのランタイムごとのフォルダも、この表に従います。
  - Linux ARM64 版で x86 と x64 を動かす方法は、下の「Linux」にあります。Linux と macOS のインストールでは、プラグインホストは `libexec/brack` に入ります。
- **実行できるアーキテクチャ。** `architectureRunsHere()` が、その PC でそのアーキテクチャのプログラムを実行できるかを答えます。Windows 11 では `GetMachineTypeAttributes`（エミュレーションも含む）、それより前は `IsWow64Process2` の本来のアーキテクチャと WOW64 の x86 で判断します。実行できないアーキテクチャのプラグインホストは起動しません。読み込みは「this computer does not run ... programs」で失敗し、スキャンは黙って飛ばします。
- **混ざった一覧とラック（`test_dll`）。** アプリが使う DLL の経路で、同じアーキテクチャと異なるアーキテクチャのプラグインを一緒に使えることを確かめます。
  - テスト用シンセの CLAP・VST2・VST3 を、このビルドの `bin` とほかのビルドの `bin`（`BRACK_TEST_OTHER_BINS`。同じ場所にあるほかのアーキテクチャのビルドと、macOS ではユニバーサル版）から集めて 1 回のスキャンにかけ、一覧に載ったものを 1 つのラックで同時に鳴らします。動かせるものはそのアーキテクチャで載り、このビルドの同じ形式のものとサンプル単位で同じ音になります。動かせないものは載らず、読み込むと断られます。
  - これだけでは整合（載るものは鳴り、載らないものは断られる）しか見られず、動くはずのものを断る誤り（例: Rosetta 2 で動くユニバーサル版が arm64 のものを断る）は見つかりません。そこで、フォルダを `<フォルダ>=<アーキテクチャ>` か `<フォルダ>=refused` で渡すと、そのとおりになることも確かめます。自分のアーキテクチャは、コンパイラが定める値（`__aarch64__` など）と比べます。
  - **`tools/arch_matrix.sh`。** 13 章の組み合わせの表を、期待を付けて回します。Rosetta 2 の修正、qemu-user のローダーの確認、`FEX` の名前探しなど、確かめる仕掛けを 1 つずつ壊した版では、どれもその行が FAIL になりました。
  - GUI のプラグインを足す一覧も、ラックと同じく、Brack と違うアーキテクチャのものにはそのアーキテクチャを添えます（`brack test synth [CLAP, x64]`）。同じプラグインの arm64 用と x64 用が並んでも見分けられるようにするためです。
  - GUI は DLL と同じコードでスキャンし（`Engine::scanPlugins`）、同じ `Engine::addPlugin` で読み込みます。GUI だけの処理は、楽器でないものを外して名前で並べることと、一覧の文字列です。そのため、アーキテクチャの組み合わせは DLL のテストで足ります。
- **スキャン。** ファイルごとにアーキテクチャを決め、そのアーキテクチャのプラグインホストで調べます（`RemoteDescriber`、4 章）。プラグインホストはアーキテクチャごとに 1 つ作り、次のファイルにも使い回します。落ちたり止まったりしたら、そのファイルを失敗にし、次のファイルでは新しく作ります。
- **解放で落ちるファイル。** 解放時に落ちるファイルも、一覧を作るところまでは正しく済むので、スキャン結果に載ります。読み込んでも、落ちるのはそのプラグインホストだけです。

### 確かめたこと（`test_isolation`、x64 と x86）

- 5 種類の終わり方（自分のスレッドでのアクセス違反、ウィンドウ処理の中でのアクセス違反、`abort()`、`__fastfail()`、返ってこない `process`）のそれぞれで、Brack と隣のプラグインが動き続けること、報告と `PluginCrashed` イベントが出てエディタが閉じ、セッションに状態が残って外せることを確かめています。そのほか、同じプロセスと別プロセスで同じ音が出ること（3 形式、もう一方のアーキテクチャのものも差 0）、相対パス、Brack と一緒に終わること、MMCSS の優先度も確かめます。
- `test_crash` は、同じプロセスと別プロセスの両方で回します。違うのは解放で落ちるファイルの扱いだけで、同じプロセスでは以後拒否し、別プロセスでは読み込み直せます。
- 1 ブロックあたりの時間も表示します。プロセスを分けたことによる上乗せは、プラグイン 1 つで 5〜6 µs です（この PC、テスト用シンセ、ブロックを休みなく続けて処理したときの値。64 フレームで同じプロセス 0.7 µs、別プロセス 6.2 µs）。プラグインを 8 つ並べると、256 フレームではプラグインどうしが並列に動く分で相殺されます（19.2 µs と 18.3 µs）。64 フレームでは相殺されません（5.0 µs と 15.0 µs）。実際のデバイスでは、ブロックの合間に休んだ CPU を起こすので、もっと長くなりえます（未計測）。Linux と macOS での値は、下の「Linux」と「macOS」にあります。
- 要求（状態の保存など）が返ってこないときの打ち切りは、時間が最短でも 10 秒なので、テストにしていません。音声処理の打ち切りと同じく、プロセスを終わらせる経路を通ります。

### Linux（`remote/*_posix.cpp`）

- **分け方。** Windows の実装を、OS によらない部分と OS ごとの部分に分けました。
  - Brack 側では `HostProcess`（`host_process.h`）を抽象クラスにし、Windows（`host_process_win32.cpp`）と POSIX（`host_process_posix.cpp`）が実装します。
  - プラグインホスト側では、Brack とのつながりを `BrackLink`（`brack_link.h`）にし、こちらも Windows と POSIX が実装します。
  - `RemotePlugin`、`RemoteDescriber`（`remote_plugin.cpp`）と、プラグインホストの中身（`plugin_host.cpp`）は、OS によらない 1 つのコードです。
- **通信。**
  - メッセージは `socketpair` 1 本で、Windows の名前付きパイプの代わりです。時間切れは `poll` で測ります。
  - 「処理して」「済んだ」は、制御ブロックの `turn`（今どちらの番か）を書き換え、futex で起こします（`futex_posix.h`）。Brack とプラグインホストは別々に共有メモリを開いているので、プロセス内だけの `FUTEX_PRIVATE_FLAG` は使いません。
    - Brack は、まず 20 µs だけ回って待ってから眠ります。眠って起こされるのに WSL2 で 12 µs ほどかかり、プラグインはそれより早く終わることが多いためです。プラグインホストは、次のブロックまで 1 ms 以上あるので、回らずに眠ります。
    - プラグインホストが消えても、futex は誰も起こしません。そのため Brack は 10 ms ごとに起き、プロセスが終わっていないかを `waitid`（`WNOWAIT`。回収はホストスレッドに任せる）で確かめます。消えたことに気づくのは最大 10 ms 遅れます。
    - プラグインホストは Brack が消えるのを待たず、`PR_SET_PDEATHSIG` で一緒に終わります（下の「Brack と一緒に終わる」）。
    - 1 ブロックの費用（WSL2 の x64、64 フレーム、プラグイン 1 つ）は、ソケットで 1 バイトずつ送る方式では 24 µs、futex だけでは 23 µs、回って待つ今の方式では 12 µs です。効いたのは回って待つことのほうです。
    - VMware の Ubuntu 24.04（仮想 CPU 16 個）では、64 フレームでプラグイン 1 つ 1.8 µs、8 つ 64 µs でした（同じプロセスでは 1.4 µs、9.7 µs）。リアルタイムの優先度でも普通の優先度でも、ほぼ同じです。
      - 1 つで上乗せがほとんど無いのは、ブロックを休みなく続けると、プラグインホストが眠る前に次のブロックの番になり、futex が眠らずに戻るためです。2 つ以上では、先に終わったプラグインホストがいちばん遅いものを待つ間に眠り、毎ブロック起こされます。
      - 8 つの上乗せ（約 55 µs）は Windows のイベント（15 µs）の約 4 倍で、Brack が眠っているプラグインホストを順に起こす費用でほぼ説明できます。眠っているスレッドを起こすと、起こす側が `FUTEX_WAKE` の中で 1 つにつき 7〜10 µs 待たされ、全員を 1 つの futex で眠らせて 1 回で起こしても減りません（8 つで 60.5 µs）。仮想 CPU への割り込み（ハイパーバイザーを経る）のためと推測しています（13 章の TODO）。
      - 実際のデバイスのように、ブロックをそれぞれの時刻に処理して合間は眠る測り方（`--block-cost` の「paced」）では、プラグインホストが毎ブロック眠ります。64 フレームで 1 つ約 30 µs、8 つ 81〜87 µs で、ブロックの長さ（1.33 ms）の 2〜7% です。1 つの約 30 µs は、起こす呼び出し（約 10 µs）と、プラグインホストが動き出すまで（約 20 µs）です。
  - 制御ブロックは POSIX の共有メモリ（`shm_open`）で、開いたらすぐに名前を消し、記述子だけをプラグインホストに渡します。出力の共有メモリはプラグインホストが作ってすぐに名前を消し、Brack は `/proc/<pid>/fd/<記述子>` から開きます。どちらが先に終わっても何も残りません。
  - 記述子は、メッセージと制御ブロックの 2 つだけを 3 番と 4 番に写して渡し（`posix_spawn` の `adddup2`）、ほかは `FD_CLOEXEC` で渡しません。写す前に、元を 5 番以上へ移します。元の番号のままでは、制御ブロックがたまたま 3 番のとき、ソケットを 3 番に写す `adddup2` がそれを上書きするためです（セッションのプラグインを同時に読み込むと、この並びになることがあります）。
  - 標準入力と標準出力は `/dev/null` にし、プラグインの `printf` が brack-cli の出力に混ざらないようにします。標準エラーはそのまま渡すので、エラーは見えます。
- **クラッシュの記録。**
  - プラグインホストは `SIGSEGV`・`SIGBUS`・`SIGILL`・`SIGFPE`・`SIGABRT`・`SIGTRAP` を受けると、制御ブロックに記録してから、そのシグナルの既定の動作で終わります。落ちた命令の位置は、スレッドの文脈（`ucontext`）から読みます。スタックがあふれたときのため、ハンドラーは別のスタック（`sigaltstack`、64 KB）で動かします。
  - 別のスタックはスレッドごとに要ります。プラグインが作るスレッドにも持たせるため、プラグインホストのプログラムが `pthread_create` を定義し、C ライブラリのものの代わりに受けます（`src/host/plugin_threads_linux.cpp`）。プログラムが書き出した名前は、プラグインからの呼び出しでも先に見つかるためです。新しいスレッドは、別のスタックを用意してからプラグインの関数を呼びます。
    - 置き換えなければ、プラグインのスレッドでスタックがあふれたときにハンドラーを動かす場所が無く、カーネルがそのままプロセスを終わらせるので、報告はシグナルの名前だけになります。置き換えると、ほかのクラッシュと同じく、どこで落ちたかが出ます。
    - 別のスタックは `mmap` で確保し、スレッドが終わるときに外して解放します。スレッドローカルの配列にすると、プログラムの静的な TLS としてすべてのスレッドのスタックから取られ、プラグインが小さいスタックで作るスレッドでは足りなくなるおそれがあるためです。
  - Brack からの呼び出しの中で落ちたときは、呼び出しの守り（11 章）が捕まえ、Brack と同じプロセスで動かすときと同じく `crashed in process: segmentation fault (0x0000000B) at libfoo.so+0x1234` と報告してから終わります。このハンドラーが記録するのは守りの外（自分のスレッド、`abort()`）で落ちたときで、`crashed in the plugin: segmentation fault (0x0000000B) at brack-test-synth.clap+0x79bf` のように報告します。
    - Windows では、自分のスレッドでのスタックあふれは `crashed in a thread or window of its own: stack overflow (0xC00000FD) at ...` になります。言い方が違うのは、受ける仕組みの範囲が違うためです。Windows の未処理例外フィルターが受けるのは、自分のスレッドとウィンドウ処理の中のクラッシュです（`abort()` は fast fail で、Brack が終了コードから報告する。上の「終わり方の扱い」）。POSIX のシグナルハンドラーは `abort()` も含めて守りの外をすべて受けるので、「the plugin」とします。
  - FEX-Emu（2609.1）の上の x64・x86 のプラグインホストでは、プラグインのスレッドでスタックがあふれても落ちずに回り続け、`process()` の中であふれると「stopped responding in process」になります。原因は FEX-Emu の側にあります。
    - glibc 2.42 からは（FEX-Emu の Fedora 44 のルートファイルシステムは 2.43）、スレッドのスタックのガードページを `madvise(MADV_GUARD_INSTALL)` の印で作るので、ガードがスタックの書き込める領域の中に残ります。FEX-Emu はそこで起きた SIGSEGV を、自己書き換えコードの監視のために自分が書き込み禁止にしたページへの書き込みと見なします。そして `mprotect` で書き込めるようにして（印には効かない）命令をやり直すので（`SyscallHandler::HandleSegfault`）、ゲストのハンドラーには届きません。メインスレッドのガードはカーネルの隙間で領域ではないので、ふつうに届きます。
    - 小さなプログラムで確かめると、ネイティブ（ARM64）と qemu-user ではどの落ち方も報告され、FEX-Emu でも、ガードページを `mprotect(PROT_NONE)` で作るもの（glibc 2.39 の Ubuntu 24.04 のルートファイルシステムなど）では報告されました。
    - Brack の側では直さず、ここに記録するだけにします。Fedora 44 のルートファイルシステムでは、x64 版と x86 版の `test_crash` と `test_isolation` がこの 2 つの落ち方で失敗します（Ubuntu 24.04 のものでは通ります）。
- **Brack と一緒に終わる。** プラグインホストは起動直後に `PR_SET_PDEATHSIG` で、Brack が終わったら `SIGKILL` を受けるようにします。
  - この合図は、プロセスではなく、プラグインホストを起動したスレッドが終わったときに来ます。すぐ終わるスレッド（上の「起動」の、プラグインを一斉に読み込むときの作業用のスレッドや、`addPlugin` を呼んだスレッド）から起動すると、そのスレッドが終わったところでプラグインホストも終わってしまいます。
  - そこで、プラグインホストは、プロセスと同じだけ続く 1 本のスレッド（`onLastingThread`）から起動します。そのスレッドはシグナルをすべて止めておき、プロセスに来るシグナルはほかのスレッドに任せます。プラグインホストは、起動したスレッドによらず、シグナルを止めずに始めます（`POSIX_SPAWN_SETSIGMASK`）。
- **オーディオスレッドの優先度**（`util/realtime_linux.cpp`）。
  - Brack の再生スレッドと、プラグインホストのオーディオスレッドをリアルタイムにします。優先度は 80 で、サウンドサーバーのスレッド（PipeWire は 88）より下です。そのスレッドが作るスレッドは、リアルタイムを引き継ぎません（`SCHED_RESET_ON_FORK`）。
  - どちらも Brack が自分のスレッドから行います。再生スレッドは最初のコールバックで行い、プラグインホストはオーディオスレッドの最初のブロックでスレッド ID を知らせるだけです（note の `audioThread`）。オーディオスレッドに D-Bus を待たせないためです。また、別のアーキテクチャのプラグインホストには、そのアーキテクチャの libdbus が無いことがあります。
  - まず `sched_setscheduler` で `SCHED_FIFO` にします。rtprio の上限（audio グループの設定など）か `CAP_SYS_NICE` があればできます。
  - できなければ RealtimeKit に頼みます（`MakeThreadRealtimeWithPID`）。libdbus は dlopen で読み込み、無ければあきらめます。RealtimeKit が許す優先度（既定で 20）までの `SCHED_RR` になります。
    - RealtimeKit は polkit に尋ね、既定では、席（seat）のあるローカルなデスクトップのユーザーのプロセスにしか許しません。SSH から起動した Brack、サービスとして動かした Brack、WSL の Brack（どれもセッションに席が無い）は `Operation not permitted` で断られ、rtprio の上限を設定するしかありません。ただし SSH からでも、`systemd-run --user` で起動したもの（ユーザーの systemd の下）は、デスクトップにログインしている間は許されます（VMware の Ubuntu 24.04 の GNOME）。
    - RealtimeKit が同時に面倒を見るのは、ユーザーあたり 15 プロセス・25 スレッドまでで、要求はユーザーあたり 20 秒に 25 回までです（既定値）。デスクトップがすでに使っている分（この VM では 6 プロセス・9 スレッド）を引くと、リアルタイムにできるプラグインホストは 9 個ほどでした。要求の回数を使い切ると、`Device or resource busy` で断られます。
  - RealtimeKit は、プロセスの `RLIMIT_RTTIME`（眠らずに動ける時間の上限）のハード上限が、RealtimeKit の `RTTimeUSecMax`（既定で 200 ms）以下であることを求めます。Brack はハード上限をその値に、ソフト上限をその半分（既定で 100 ms）にします（もとの上限のほうが低ければ、そちらを残す）。ソフト上限を超えたスレッドは `SIGXCPU` を受けて普通の優先度に戻ります（アプリが `SIGXCPU` を自分で扱っていなければ）。ハード上限を超えると、カーネルがプロセスを `SIGKILL` で終わらせます。
    - 普通の優先度には `SCHED_OTHER | SCHED_RESET_ON_FORK` で戻します。リアルタイムにするときに付けた `SCHED_RESET_ON_FORK`（RealtimeKit も付ける）は、特権の無いスレッドには外せず、外そうとすると EPERM で断られるためです。戻せなければ、リアルタイムのまま上限まで動き、プラグインホストが SIGKILL で終わります（「crashed: Killed (signal 9)」）。
  - 結果はログに出します。同じ結果は 1 度だけです。
  - スキャン用のプラグインホストはオーディオスレッドを作りません（プラグインを作ったときに作る）。RealtimeKit の要求の回数を使わないためです。
- **既定の出力デバイスの切り替え**（`Engine::checkOutputRoute`、`audio_output.cpp`）。
  - Brack は 1 秒ごとにシステムの既定のデバイスを確かめ、変わっていれば開き直します（Windows と同じ）。
  - Linux の miniaudio は PulseAudio のインターフェース（PipeWire では pipewire-pulse）で、名前を指定しない「システムの既定」を、サウンドサーバーが動かせるストリームとして開きます。PipeWire（WirePlumber）は、既定が変わるとそのストリームをすぐに新しいデバイスへ移します。そこへ Brack が開き直すと、音がもう一度途切れます（VMware の Ubuntu 24.04 では、移った約 0.5 秒後に 10〜40 ms）。
  - そこで、サウンドサーバーがストリームを動かした（miniaudio の `rerouted` の知らせ）ときは、開き直さず、新しいデバイスを記録するだけにします。ログは `audio: now playing on X (was Y), moved there by the sound server` です。
    - 既定が変わった直後で、まだ動かされていないこともあるので、新しい既定は 1 回分（1 秒）待ちます。それでも動かされなければ、開き直します。ストリームを本物のデバイスに固定したとき（`target.object`。ミキサーで手で動かしたときと同じ）は、PipeWire が動かさないので、こちらになります。
    - 名前を指定したデバイスや、ALSA・JACK で開いたものには、この扱いを当てはめません。
  - 動かされたあとは、サウンドサーバーが新しいデバイスのレートに変換します（Brack のストリームのレートは変わらない）。Windows で開き直すのは、miniaudio の線形補間の変換を避けて Brack の SRC を使うためです。PipeWire の変換は窓付き sinc で線形補間よりよいので、こちらに任せます。
  - ALSA で開くとき（PipeWire の ALSA プラグイン）の既定のデバイスは「Default ALSA Output (currently PipeWire Media Server)」で、どのデバイスが既定でも名前が変わらないので、Brack は開き直しません。ストリームは PipeWire が既定に合わせて動かします（下の「ALSA プラグイン越しの途切れ」も参照）。
  - サウンドサーバーの無い ALSA だけの環境と JACK サーバーには、動いている間に変わる「既定のデバイス」がそもそもありません（ALSA は設定ファイル、JACK は起動時に決めた 1 つのデバイス）。
  - バックエンドは環境変数 `BRACK_AUDIO_BACKEND`（`pulseaudio`、`alsa`、`jack`。miniaudio の名前で、大文字小文字は問わない）で選びます。指定しなければ miniaudio が最初に開けたもので、PipeWire の環境では PulseAudio のインターフェースです。
  - JACK（pipewire-jack）では、既定に追従しません。miniaudio の JACK のクライアントは自分の出力ポートを物理ポート（`JackPortIsPhysical`）につなぎ、pipewire-jack はそれを既定の出力ではなく ALSA の実機のノードにするので、既定を移してもつながりは変わりません。JACK では、つなぎ先はクライアント（か、パッチベイでユーザー）が決めるもので、WirePlumber も手でつないだリンクを動かしません。Brack のデバイスの一覧も JACK では「Default Playback Device」の 1 つだけです。追従しないのが JACK の使い方として正しい形です。
    - VMware の Ubuntu 26.04 でこの経路に出る「audio device stopped」は、VM の HD Audio のエミュレーションが止まるためで（下の「Apple シリコンの VMware Fusion の音声」）、既定を移すこととは関係ありません。
  - **Apple シリコンの VMware Fusion の音声。** Ubuntu 26.04（ARM64）の VM では、Brack を使わなくても PipeWire の出力が途切れます。
    - `pw-play` で正弦波を流すだけでも、出力ノードの xrun は、quantum 2048、44.1 kHz、headroom、period-size、3D アクセラレーションのどれを変えても 14 秒に 33〜73 回ありました。途切れなかったのは quantum 4096（85 ms）だけです。VM の headroom が下がって途切れる Ubuntu のバグ（LP #2127250）の修正（26.04 の wireplumber 0.5.13）が効いていても途切れ、Mac 側の VM のログ（`vmware.log`）には `HDAudio: Unhandled REG write ... Stream Synchronization` が多数出ています。
    - PipeWire は、VM の中（`cpu.vm.name` がある）では `clock.min-quantum` を 1024 にします（`pipewire.conf` の規則）。そのため、VM の quantum は 1024 より小さくなりません。
    - PulseAudio に替えても、Brack のバッファが小さいと間に合いません。5 台のラックで 20 秒鳴らしたときの PulseAudio のアンダーランは、バッファ 256 で 6,569、2048 で 17 でした。`paplay` で正弦波を流すだけで 24 なので、2048 では Brack は途切れを増やしていません。そのぶん音は遅れます（周期 4096 フレーム、44.1 kHz で約 93 ms）。
    - 残る途切れは VM の限界として扱います。x64 の PC の VMware Workstation（Ubuntu、PipeWire）では途切れなかったので、違いは Apple シリコンの VMware Fusion の音声の経路にあると見ています。途切れたときに Brack が悪化させないこと（MIDI の順序、プラグインホストの SIGKILL、デバイスが止まったという判断）は、12 章とこの章の仕組みで扱っています。
  - **ALSA プラグイン越しの途切れ。** VMware の Ubuntu 26.04（PipeWire 1.6.2）で、既定の出力を null sink にして Brack を ALSA のバックエンド（バッファ 256 フレーム、周期 2 つ）で鳴らすと、21 ms ごとに 10 ms の無音がありました。
    - 原因は、PipeWire のグラフの 1 周期（quantum）が、ALSA のバッファ（周期の数 × 周期）より大きいことです。ALSA プラグインは 1 周期ぶんを一度に取り、バッファに無いぶんを無音で埋めます。quantum はクライアントが求める遅れに合わせて `clock.min-quantum` まで下がりますが、VM の中では 1024 より下がりません（上の「Apple シリコンの VMware Fusion の音声」）。miniaudio のコールバックを数える小さなプログラム（cbprobe）でも、周期 256 × 2 では実時間の 50% のフレームしか渡されず、× 4 と × 8 では 100% でした。
    - そこで、ALSA のバックエンドで開くデバイスの名前に「PipeWire」があるとき（既定の「Default ALSA Output (currently PipeWire Media Server)」、名前で選んだ「PipeWire Sound Server」）、バッファが 2048 フレーム（PipeWire の既定の `clock.max-quantum`）以上になるように周期の数を増やします（256 なら 8 つ）。周期（コールバック 1 回の長さ）は変えません。
      - これで同じ条件の無音は無くなりました。そのぶん遅れは増えます（バッファ 256 で 2048 フレーム、48 kHz で 43 ms）。
      - 実機の ALSA（`hw:` など）は周期 2 つのままです。
      - PipeWire の環境でこの経路を通るのは、pipewire-pulse が無いときか `BRACK_AUDIO_BACKEND=alsa` のときだけです。
      - `clock.max-quantum` を 2048 より大きくし、quantum もそこまで上げた環境では、まだ途切れます。
    - x64 の VM（VMware Workstation の Ubuntu 24.04、PipeWire 1.0.5、`clock.min-quantum` 1024）では、周期 256 フレームなら無音はありません。ところが周期を 128 フレーム以下にすると、バッファが 2048 フレーム以上でも音の約半分が無音でした（リアルタイムの優先度でも同じ）。cbprobe でも実時間の 32〜49% のフレームしか渡されず、コールバックがまとめて来て、次は 30〜100 ms 後でした。バッファの大きさでは足りず、小さな周期では、PipeWire の ALSA プラグインがアプリを起こさない間があると見ています（原因は確かめていない。13 章の TODO）。
- **アーキテクチャ。**
  - `architectureLauncher()` が、各アーキテクチャのプラグインホストを起動する方法を決めます。
    - x64 の Linux での x86 は、32 ビットのローダー（`/lib/ld-linux.so.2`）があればそのまま起動します。
    - ARM64 の Linux での x64・x86 は、binfmt_misc の登録があればそのまま起動し、無ければ PATH の FEX-Emu を前に付けて起動します。PATH では今の名前の `FEX` を先に探し、次に以前の名前の `FEXInterpreter` を探します。
      - Box64・Box86 は候補にしません。どちらも本物では試しておらず、Box86 は 32 ビットの ARM の無い Apple シリコンでは動かないためです。
  - C++ の実行時ライブラリは、どのプログラムにも静的にリンクします（`-static-libstdc++ -static-libgcc`）。そのため、x86 のプラグインホストに要るのは 32 ビットの C ライブラリだけです。
    - 静的にリンクした実行時ライブラリは、libbrack.so やプラグインからは書き出しません（`-Wl,--exclude-libs,ALL`）。書き出すと、読み込んだアプリ自身の libstdc++ のシンボルを横取りするためです。
  - **配るプラグインホストの glibc。** Ubuntu 26.04 のクロスコンパイラ（glibc 2.43）で作った x86 のプラグインホストは、そのままでは `GLIBC_ABI_GNU_TLS` を要求し、FEX-Emu の Ubuntu 24.04 のルートファイルシステム（glibc 2.39）では起動しません。
    - 付けるのはリンカーです。binutils 2.46 の i386 の `ld` は、`___tls_get_addr` を参照するオブジェクトがあると、既定でこの版の要求を出力に付けます。i386 の `___tls_get_addr` が SSE のレジスタを壊す不具合の修正（BZ #32996、glibc 2.42 の NEWS）を求める印と見ています。
    - 参照は、`-fPIC` の `libbrack_core.a`（`thread_local`）と静的な libstdc++ から来ます。ただ、実行ファイルではリンカーが TLS のアクセスを `%gs` の直接参照に緩和するので、プラグインホストは実際には 1 回も呼びません。libbrack.so とテスト用シンセは呼びますが、Brack の x86 のコードは SSE を使わないので（Ubuntu の i686 の g++ の既定）、この不具合の影響を受けません。
    - そこで `-Wl,--no-gnu-tls-tag` で外します（CMake の `check_linker_flag` で、受け付けるリンカーにだけ。x64 と ARM64 の `ld` は受け付けません）。`-mtls-dialect=gnu2` では `GLIBC_ABI_GNU2_TLS` に替わるだけで、glibc 2.39 にはそれも無いので直りません。x86 のコードで SSE を使うようにするときは、この前提が崩れます。
    - 外したあと、x86 版と x64 版のどの実行ファイルも libbrack.so も、要求する最も新しい glibc は 2.38 です（`__isoc23_strtol` などの C23 の置き換えで、Ubuntu 23.10・Fedora 39 から）。それより古いルートファイルシステム（Ubuntu 22.04、Fedora 38）で動かすには、古い glibc のシステムルートでビルドするしかありません。配布物は、そのために glibc 2.28 の環境（manylinux_2_28 のコンテナ）でビルドします（development.ja.md の「リリース」）。
    - クロスビルドの x64・x86 のプラグインホストは、ビルドの後に `cmake/check_glibc_needs.cmake` が `readelf -V` で確かめ、2.39（Ubuntu 24.04）より新しい `GLIBC_2.x` か `GLIBC_ABI_*`（`DT_RELR` を除く）を要求していれば、ビルドを失敗させます（印を外さない `-DBRACK_LINKER_NO_GNU_TLS_TAG=0` では「brack-host-x86 needs GLIBC_ABI_GNU_TLS」）。配布物は、`tools/check_release_files.sh` が同じスクリプトで、どの ELF も glibc 2.28 より新しい版を要求していないかを確かめます。
  - **x86 版が x64 のプラグインを断る文。** x86 版は x64 のプラグインホストを同梱しないので、x64 のプラグインを断ります。その文は、「同梱していない」と「動かない」を分けます。
    - `architectureLauncher` は、x86 版からは、カーネルが x86_64 と答えれば（`uname`。x64 のカーネルは 32 ビットのプロセスにもそう答え、FEX-Emu もそうする）x64 のプログラムは動くとします。同梱の有無は、その次のプラグインホストのファイルの確認が答えます（「no plugin host for x64 plugins (brack-host-x64 is not installed beside Brack)」）。混ぜると、x64 の PC で「this computer does not run x64 programs」という誤った文になります。
    - Windows と macOS は、もともと「動くか」と「同梱しているか」を分けて確かめています。
    - `tools/arch_matrix.sh` の Linux の行は、断られる理由まで期待として指定します（`test_dll` の `=no-host` / `=not-run`。FEX-Emu の上の x86 版で x64 は `no-host`、エミュレーター無しの ARM64 版で x64・x86 は `not-run`）。
- **場所。**
  - ビルドではすべて `bin` に入ります。インストールでは、プラグインホストは `libexec/brack` に入ります。
  - プログラムと libbrack.so は、自分の隣を探し、無ければ `../libexec/brack` を探します。
- **使うときに読み込むライブラリ。** libasound と libX11 は、libdbus と同じく、リンクせずに使うときに dlopen で読み込みます（`midi/alsa/alsa_seq_input.cpp`、`plugin/host_window_x11.cpp`）。リンクすると、MIDI ポートもエディタも使わないサーバーやコンテナで、libbrack.so、CLI、プラグインホストが起動しないためです。
  - 無ければ、MIDI ポートとエディタを開くところで、ライブラリの名前を挙げて失敗します。
  - GUI は X11 と OpenGL が無ければ動かないので、libGL をリンクします。libX11 は GLFW が自分で読み込みます。
- **イベントループ**（`host_thread_posix.cpp`）。
  - ホストスレッドは `poll()` で待ちます。起こすのはパイプで、タイムアウトは次のタイマーまでの時間です。ファイル記述子を見張れます（`HostThread::watchFd`）。見張るのは X11 の接続と、プラグインが登録するもの（CLAP の `posix-fd-support`、VST3 の `IRunLoop`）です。
  - epoll ではなく `poll()` にしたのは、見張るものが数個で、macOS でもそのまま使えるためです。
- **エディタ**（`host_window_x11.cpp`）。
  - X11 のウィンドウを作り、プラグインのウィンドウをその子にしてもらいます（CLAP の x11 のウィンドウ、VST3 の `X11EmbedWindowID`、VST2 の Window）。X11 の接続はホストスレッドごとに 1 本で、窓が無くなれば閉じます。
  - 大きさを変えられない窓は、最小と最大を同じにしてウィンドウマネージャーに伝えます。ユーザーのリサイズは `ConfigureNotify` で知り、自分で頼んだ大きさと区別します。
  - 倍率は X のリソースの `Xft.dpi` から読みます。`XResourceManagerString` は接続を開いたときの値のままなので、ルートウィンドウの `RESOURCE_MANAGER` を直接読み、その変化を `PropertyNotify` で知って、すべてのエディタに知らせます（CLAP の `set_scale`、VST3 の `setContentScaleFactor`）。
  - XEmbed（freedesktop.org の取り決め、版 0）の埋め込む側です。`_XEMBED_INFO` を付けた最初の子に `XEMBED_EMBEDDED_NOTIFY` を送り、`XEMBED_MAPPED` に従って表示し、隠します。
    - キーボードのフォーカスが外から窓に来たら活性、外へ出たら非活性にします（窓の中での移動は数えません）。窓そのものに来たフォーカスは、子から戻ってきたもの（`NotifyInferior`）も含めて子に渡し、`XEMBED_FOCUS_IN` を送ります。窓の中の子にフォーカスがあるので、キー入力はプラグインのウィンドウに直接届きます。
    - プラグインのウィンドウはいつ消えるか分からないので、それへの要求は X のエラーを捕まえながら出します（`ErrorTrap`）。Xlib の既定では、エラーでプロセスが終わるためです。エラーのハンドラーはプロセスで 1 つなので、ほかの接続のエラーはそれまでのハンドラーに渡します。
    - 扱っていないもの: タブでのフォーカスの移動（`XEMBED_FOCUS_FIRST` / `LAST`、`FOCUS_NEXT` / `PREV`）、アクセラレーター、モーダルの通知、2 つ目からの子。
  - CLAP は、開いたあとに `can_resize` も聞き直します（LSP は `set_parent` のあとでないと、リサイズできると答えない）。大きさを聞き直すのと同じ理由です（1 章）。
  - VST3 の `IRunLoop` は、エディタごとに作って `IPlugFrame` から渡します。エディタを閉じるとき、プラグインが登録したまま残したものも外します。プラグインが落ちていれば、ハンドラーは解放しません（プラグインのコードを呼ばないため）。
  - エディタの無いプラグインのため、インスタンスごとのホストのコンテキスト（`initialize` に渡すもの）からも `IRunLoop` を渡します。インスタンスを壊すとき、`terminate` の後に残っているものを外します。外した後もプラグインが `IRunLoop` を持っていることがありますが、登録は断ります。モジュールのコンテキスト（`setHostContext`）は、インスタンスに属さないので渡しません。
  - Ubuntu のパッケージの DISTRHO の Nekobi（CLAP、VST3、VST2）と LSP の Compressor Stereo（CLAP）のエディタは、描画され、窓に収まります。Nekobi の VST3 は `IRunLoop` にタイマーを登録します。
- **GUI**（`src/gui`）。
  - GLFW と Dear ImGui の GUI は、Linux でもそのまま動きます。Linux のために足したのは、ファイルダイアログ（`file_dialog_posix.cpp`）と、GLFW を X11 だけでビルドする設定（`GLFW_BUILD_WAYLAND OFF`）です。Wayland のデスクトップでは Xwayland で動きます。エディタも X11 なので揃えました。
  - ファイルダイアログは、まずデスクトップのポータル（xdg-desktop-portal の `org.freedesktop.portal.FileChooser`）に D-Bus で頼みます。親の窓（`x11:<窓の ID>`）を渡すので、ダイアログは Brack の窓に結びつきます。Flatpak などのサンドボックスの中でも同じように動きます。
    - 答えは要求のオブジェクトの `Response` シグナルで来ます。呼ぶ前に、その経路をポータルからのものだけに絞って待ちます。届いたシグナルは、送り主が呼び出しに答えたポータルと同じかも確かめます。マッチの規則だけでは、宛先を指定したシグナルを止められないためです。
  - ポータルが無ければ（libdbus が無い、セッションバスが無い、FileChooser が無い）、zenity か kdialog を子プロセスで起動し、選んだパスを標準出力から読みます。kdialog には `--attach` で窓を渡します。zenity は 4 から `--attach` が何もしないので、結びつきません。
  - 最初に開く場所は、同じフィルターで最後に選んだファイルのフォルダで、まだ無ければホームフォルダです。
  - libdbus は、RealtimeKit と同じく、使うときに dlopen で読み込みます（`util/dbus_linux.cpp`）。
  - ダイアログは専用のスレッドで動かし、GUI は描画を続けます。その間、Brack の操作は「Waiting for the file dialog...」のモーダルの後ろで待ちます。選んだパスは次のフレームで受け取ります。GUI のループがダイアログを待つと、窓が描き直されず、ウィンドウマネージャーの応答確認にも答えられないためです。
    - Windows も同じです（ダイアログのスレッドは COM のシングルスレッドアパートメントにし、Brack の窓を持ち主にする）。ダイアログを開いたまま窓を閉じると、ダイアログを閉じてから終わります。
  - 「From file...」で VST3 バンドルの中のファイルを選ぶと、そのバンドルを読み込みます。ファイルを選ぶダイアログではフォルダ（バンドル）を選べず、Linux ではバンドルの中の実行ファイルが `.so` で VST2 と見分けられないためです。
  - WASAPI の排他モードは、GUI では Windows でだけ出し、音声出力は Windows 以外では無視します（Windows で保存したセッションが指定していても）。
- **MIDI ポート**（`midi/alsa/alsa_seq_input.cpp`）。
  - ALSA シーケンサーを使います。機器のポートと、ほかのプログラムのポートが同じ一覧に並び、PipeWire の環境でもそのまま使えます。ALSA の開発用ファイルがあるときだけこちらをビルドし、無ければポート無し（`midi/posix/`）です。
  - Glosa の Linux 版の MIDI（`src/Glosa.Midi.Linux`）に倣いました。
    - 一覧に出すのは、MIDI を運ぶ型（`MIDI_GENERIC`・`SYNTH`・`APPLICATION`）で、購読して読めて、隠されていない（`NO_EXPORT` でない）ポートです（RtMidi と同じ選び方）。
    - 名前はポートの名前で、ほかのクライアントのポートと名前が重なるときだけ、クライアントの名前を括弧で添えます。クライアントの名前だけで区別しないのは、名前を付けないプログラムのクライアント名が「Client-」と番号になり、起動のたびに変わるためです。括弧の有無はほかのポートが増減すると変わるので、開くときはもう一方の名前でも探します。それでも同じ名前になるポート（クライアントの名前も同じ、同じ機種のインターフェース 2 台）は、クライアントとポートの番号の順に、2 つめから「名前 (2)」などと名付けます。ALSA には機器ごとの一意の ID が無いので、この順は差した順で変わることがあります。
    - Brack 自身のクライアント（名前が「Brack」で、プロセス ID が同じもの）は外します。
  - 開くポートごとに、シーケンサーのクライアント（「Brack」）とポートを 1 つずつ作り、専用のスレッドで読みます。ポートどうしが影響し合わず、閉じればクライアントごと消えます。機器の入力は入力元からつなぎ（`snd_seq_connect_from`）、そのポートは `NO_EXPORT` にしてほかのプログラムに見せません。仮想ポートは、ほかのプログラムがつないで送れるポートです。
  - 入力元が消えたことは、つながりが外れた知らせ（`SND_SEQ_EVENT_PORT_UNSUBSCRIBED`）で知ります。入力元のポートが消えたときも、プログラムが終わったときも、`aconnect -d` で切られたときも届くので、システムの告知（`0:1`）を購読する必要はありません（この知らせの処理だけでテストが通ります）。
  - イベントは alsa-lib のデコーダでバイト列に戻します（ランニングステータスは使わない）。SysEx は区切られて届くので、F0 から F7 までつないで 1 つにします。1 MB を超えるものは捨てます（Windows と同じ）。
  - **受信の時刻**（`MidiReceiveFn` の `whenNs`）。ポートに、シーケンサーのキューの実時間でタイムスタンプを付けさせます（`snd_seq_port_info_set_timestamping`）。カーネルが届けるときに付けるので、Brack の読むスレッドが起きるまでの揺れが入りません。キューはプロセスに 1 つで（一覧用のハンドルに作り、ポートが開いている間だけ動かす）、Brack のポートはどれも同じキューで印を付けます。区切って届く SysEx は、最初の断片の時刻です。
    - キューの時計は、hrtimer のティックに、最後のティックからの CLOCK_MONOTONIC の進みを足したもので、始めたときに 0 です。始めたときの steady_clock（libstdc++ では CLOCK_MONOTONIC）を 1 度測って足すだけでは足りません。15 分でキューの時計が CLOCK_MONOTONIC より 252 ms 進んだことも、もう 1 つのキューを始めたときに 1 ms 戻ったこともあるためです。
    - そこで、印から読むまでの時間だけをキューの時計で測ります。読んだときにキューの今の時刻を尋ね、「今の steady_clock −（キューの今 − 印）」を受信の時刻にします。キューの時計がずれても、その間（µs からミリ秒）のぶんしか効きません。尋ねるのは 1 メッセージに 1 回の ioctl です。
    - ティックは `snd_seq_queue_timer_set_resolution` で 6250 Hz にします（シーケンサーの上限。既定は 1000 Hz）。ティックが遅れると、次のティックまで、その遅れの分だけ時計が早く読めるためです。費用は、ポートが開いている間の 1 秒あたり 6250 回の割り込みです。
      - VMware の Ubuntu 26.04 で、別のクライアントから 10 ms ごとに送り、送る直前の CLOCK_MONOTONIC と比べた 1〜99 パーセンタイルの幅は、1000 Hz では印が 477 µs、読むスレッドの時刻が 326 µs で、印のほうが悪くなりました。6250 Hz では印が 18 µs、読むスレッドが 32 µs でした。CPU を 8 スレッドで使い切ると、印は 16 µs のまま、読むスレッドは 865 µs になりました。VM の仮想 CPU が休んでいるときにティックが遅れ、負荷があると遅れないためと見ています。
  - **MIDI の時刻の計測**（`tools/midi-timing`。12 章）。Linux では、送り手は ALSA シーケンサーのポート（`AlsaSeqSource.cs`）で、Brack はそれを機器の入力として名前で開きます。`midi` はすぐに送り、`midi-ahead` はツールのキューに時刻を付けて置き、シーケンサーがその時刻に届けます。`midi-zero` も、すぐに送るのと同じです（ALSA では Brack のポートが必ず印を付ける）。VMware の Ubuntu 26.04 では、どの送り方でも届かなかったものは 0 でした。
    - PulseAudio（44.1 kHz、バッファ 2048）: 揺れの幅 0.5〜8.9 ms、順序の入れ替わりとデバイスの止まりは 0。
    - PipeWire の PulseAudio のインターフェース、null sink（48 kHz、バッファ 512）: 揺れの幅 0.05〜0.15 ms（`midi-ahead` は、ツールのキューのティックの揺れが足されて 0.25〜0.33 ms）。macOS と同じ水準です。
    - 同じく HD Audio: 揺れの幅 230〜1030 ms で、「audio device stopped」が何度も出ます。開き直しても守る順序を持ち越すので（12 章）、順序の入れ替わりは 0 です。
    - サウンドサーバーの無い ALSA（PipeWire を止め、`BRACK_AUDIO_BACKEND=alsa` で「HD-Audio Generic, Generic Analog」、周期 1024）: 揺れの幅 34〜49 ms、順序の入れ替わり 0。どの回も、始めに 1 回だけ止まったと判断しました。12 章の「最初の長い間隔は、まだ覚えていないので、一度だけ止まったと判断することがあります」に当たります。
    - **x64 の VM**（VMware Workstation の Ubuntu 24.04、PipeWire 1.0.5、RealtimeKit で SCHED_RR 20）。どの送り方でも、届かなかったもの、順序の入れ替わり、デバイスの止まりは 0 でした。
      - 揺れの幅は、既定の出力（VMware の ES1371。PulseAudio のインターフェース、周期 480）と ALSA のバックエンド（周期 256）で 22〜24 ms、null sink（周期 480）で 6.1〜6.6 ms です。
      - ES1371 は実時間より遅く進みます（約 95.5%。cbprobe でも 95.4%）。時計を下げる規則がこれに付いていきます（12 章）。残る 22〜24 ms は、VM の音声デバイスと PipeWire の quantum（1024 フレーム、21.3 ms）によると見ています。
      - null sink の 6 ms は、quantum（1024）が周期（480）より大きく、コールバックが 2〜3 回まとめて来るためと見ています。揺れは 1 周期（10 ms）より小さく、メッセージが周期の頭に寄ってはいません。
      - 計測の途中で PipeWire を 1 秒と 0.6 秒止めると、「audio device stopped」が出てデバイスを開き直すことがありましたが、すべて届き、入れ替わりは 0 でした。
- **x64 の Linux の組み合わせの表**（`tools/arch_matrix.sh` の `linux_x64`）。x64 版と x86 版を、qemu-user の登録とローダーがある場合、無い場合、登録を切った場合で回し、x64 版は 32 ビットの C ライブラリを隠した場合でも回します。ARM64 版は qemu-user で回します。
  - 32 ビットの C ライブラリは、そのテストだけのマウントの名前空間（`sudo unshare --mount`）で、ローダーのあるフォルダ（`/usr/lib32`）を空のフォルダで覆って隠します。ほかのプログラムには影響しません。
    - ローダーの名前を変えて隠す方法は採りませんでした。システム全体が変わり、スクリプトが途中で殺されると戻らないためです。名前空間なら、プロセスが終われば消えます。
    - sudo の要らない `unshare -rm`（ユーザーの名前空間）も採りませんでした。Ubuntu 24.04 は AppArmor で特権の無いユーザーの名前空間を制限していて（`kernel.apparmor_restrict_unprivileged_userns=1`）、`uid_map` を書けないためです。
  - 登録を切る行と隠す行でも、ARM64 のローダーを渡します。切り替えに失敗して登録が残っていれば、ARM64 のプラグインが期待の「not-run」ではなく「no plugin host」で断られ、その行が失敗するので、切り替えの失敗を見逃しません。

### macOS

- **ホストスレッドはメインスレッド。** macOS のプラグインは、メインスレッドの仕事（エディタ、タイマー、JUCE のメッセージなど）を AppKit のメインスレッドでするものと決めています。そこでホストスレッドを、プロセスのメインスレッドのディスパッチキューにしました（`host_thread_mac.cpp`）。エディタだけをメインスレッドに出す分け方は、CLAP のメインスレッドが 2 つになり、プラグインのタイマーも動かないのでやめました。
  - メインスレッドを持つのはプロセスの持ち主です。brack-cli、プラグインホスト、テストは本来の仕事を別のスレッドでし、メインスレッドで NSApplication を回します（`util/main_thread.h` の `runWithMainLoop`）。GUI では GLFW のループがそのまま回します。DLL を使うアプリには、メインスレッドのランループを回してもらいます（brack.h）。
  - メインスレッドがループを回していないときのため、`invoke` は、頼んだ仕事が 10 秒たっても始まらなければ、一度だけ警告をログに出します。
  - タイマーと記述子の見張りは、同じキューのディスパッチソースです。記述子が閉じられると、macOS の `poll` は `POLLIN|POLLHUP` を返します（Linux は `POLLHUP` だけ）。そこで読むものが無ければ `FdRead` を外し、Linux に合わせました。
  - タイマーと見張りの関数は、自分のソースを外してもかまいません。libdispatch が取り消しのハンドラー（ソースの持ち物を解放する）を走らせるのは今のハンドラーが戻った後なので、関数は写さずにそのまま呼びます。
  - 見張りは頼まれた出来事ごとにソースを 1 つ作るので、何も頼まない見張りは何も知らせず、Linux と違って `FdError`（相手が閉じた）も届きません（`host_thread.h`）。
  - メインスレッドから呼ばれると、ホストスレッドの上で呼ばれたのと同じになります。そのときセッションの読み込みは、プラグインを 1 つずつ作ります。
- **プラグインホストとの通信。** Linux と同じ実装に、次を足しました。
  - futex の代わりに、`os_sync_wait_on_address` / `os_sync_wake_by_address_all` の共有メモリ用（`OS_SYNC_WAIT_ON_ADDRESS_SHARED`）を使います。これが macOS 14.4 からなので、それより前は対象にしません（`CMAKE_OSX_DEPLOYMENT_TARGET` 14.4）。
  - Brack と一緒に終わるため、kqueue で Brack のプロセスの終わり（`EVFILT_PROC`、`NOTE_EXIT`）を待つスレッドを置きます。
  - `MSG_NOSIGNAL` が無いので、ソケットの両端に `SO_NOSIGPIPE` を付けます。起動では `POSIX_SPAWN_CLOEXEC_DEFAULT` で、渡す記述子と標準エラー以外を閉じます。
  - 出力の共有メモリは、プラグインホストが開いてすぐに名前を消し、記述子を次のメッセージに付けて送ります（`SCM_RIGHTS`）。Brack は届いた記述子をためておき、古いものから順に出力として開きます。Linux と同じく、どちらのプロセスが途中で終わっても名前は残りません。
  - プラグインホストは窓も自分の音も無いので、App Nap の対象になりえます。そこで `NSActivityLatencyCritical` と `NSActivityUserInitiatedAllowingIdleSystemSleep` の活動を宣言します（brack-cli とテストも同じ関数を通る）。Brack.app は音を出すので、もともと対象外です。
  - 1 ブロックの費用（`test_isolation`、Apple M4 Pro、ブロックを休みなく続けたとき）は、64 フレームでプラグイン 1 つ 1.3 µs、8 つ 21.5 µs、256 フレームで 8 つ 23.1 µs です（同じプロセスでは 1.8 µs、5.9 µs、16.2 µs）。1 回の計測なので、1 つのときの同じプロセスとの大小には意味がありません。
- **オーディオスレッドの優先度。** Brack の再生スレッドは Core Audio のスレッドで、もともと time-constraint です（最初のコールバックの中で `thread_policy_get` を使って確かめた）。プラグインホストのオーディオスレッドは、活性化ごとの最初のブロックで自分を time-constraint にし（周期はブロックの長さ、計算時間はその半分）、オーディオのワークインターバル（`AudioWorkIntervalCreate`）に入ります。ブロックごとに、処理の始めに締め切りを（`os_workgroup_interval_start`）、終わりに終えたことを（`os_workgroup_interval_finish`）知らせます。結果は Brack に知らせ、Brack がログに出します。
  - ワークインターバルに入れるのは、Apple シリコンでは time-constraint だけで性能コアに載るとは限らないためです。重い VST3 のプラグインを 256 フレーム・44.1 kHz で鳴らすと、細かく音が途切れました。オーディオのコールバックが周期を超えるたびにそのプラグインのプラグインホストを待っていて、プラグインは眠らされていませんでしたが、プラグインホストが性能コアで動いた時間（`proc_pid_rusage` の `ri_user_ptime`）は約 10% でした。
  - 同じ曲をプラグインに直接流して 30 秒測ると、ワークインターバルに入れることで、周期を超えたブロックが 12〜20 から 1〜2 に、性能コアの割合が 10〜11% から 52〜53% になりました。実際の Brack.app でも音飛びは聞こえなくなりました。計算時間を周期の半分から 9 割に広げても変わりませんでした。
  - ワークインターバルを作るのに約 100 ms かかるのは、プロセスで 1 つめだけです。最初のブロックの中で作るとそのブロックが遅れるので、プラグインホストの起動時（`BrackLink::open`）に作っておきます。
  - プラグインが自分で作るスレッド（処理を分けるためのものなど）は、このワークインターバルに入りません。VST3 にも CLAP にも、ホストのワークグループをプラグインに渡す仕組みがありません。
  - DLL を使うアプリでは、同じプロセスで動かし、ワークグループに入っていないアプリのスレッドから `brack_render` を呼ぶときだけ、同じ曲で周期を超えたブロックが 9〜11、性能コアが 37〜41% になりました（プラグインホストで動かすときと、`brack_start` で Core Audio のスレッドから描画するときは 54〜58%）。この場合は、アプリにスレッドをワークグループに入れてもらいます（brack.h）。`brack_render` の中で Brack が入れないのは、スレッドが入れるワークグループは 1 つだけで、アプリがあとでデバイスのワークグループに入れなくなるためです。
- **クラッシュの封じ込め。** Linux の実装（シグナル）がそのまま効きました。デバッガーがついていなければ、Mach 例外はシグナルになります。命令の位置は `uc_mcontext->__ss`（arm64 は `__pc`、x64 は `__rip`）から読みます。スタックあふれはガードページに当たるので、セグメンテーション違反ではなくバスエラーとして報告されます。
  - プラグインが自分で作ったスレッドでのスタックあふれは、Mach の例外で受けます。プラグインホストのスレッドが Mach の例外（`EXC_BAD_ACCESS`）を先に受け、Brack がシグナル用のスタックを用意していないスレッドで、壊れた番地がスタックポインターのすぐそばなら、スタックあふれとして落ちた場所を記録します。例外はどれも断るので、カーネルはその後も今までどおりシグナルを届け、Brack のガード（`runGuarded`）も変わらず効きます（断った後もシグナルが届き、`siglongjmp` で戻れることは、小さなプログラムで確かめた）。デバッガーがついているときは、同じ口を使うので入れません。
  - Linux のように、プラグインホストのプログラムが `pthread_create` を定義して受ける方法（上の「Linux」の「クラッシュの記録」）は、macOS では効きません。プラグインは `pthread_create` を libSystem のものとして結び付けているので、プログラムが同じ名前を書き出しても使われないためです（割り込めるのは、起動時に読み込まれるライブラリだけ）。
  - シグナルだけでは、このスタックあふれが arm64 では記録されずに「Illegal instruction: 4」で終わり、Rosetta 2 の x64 では記録されました。シグナルの届き方が、ネイティブと Rosetta 2 で違います。
- **プラグインのバンドル。** バンドルの中の実行ファイルの名前は、`Contents/Info.plist`（XML のもの）の `CFBundleExecutable` から読みます。読めなければバンドルの名前、それも無ければ `Contents/MacOS` のただ 1 つのファイルです。VST3 の `bundleEntry` にはバンドルの `CFBundleRef` を渡し、`bundleExit` の後で解放します。
- **エディタ。** `host_window_mac.mm`。自分の窓のときは NSWindow に、アプリの窓の中のときはその NSView に、左上を原点にした（`isFlipped`）NSView を入れ、プラグインはそこに自分のビューを入れます。大きさはポイントで、拡大は OS がするので、CLAP の `set_scale` は呼びません。NSView はプロセスをまたげないので、プラグインホストのプラグインはアプリの窓に入れられず、そう報告します。
- **MIDI ポート。** CoreMIDI（`midi/coremidi/`）。`WithProtocol` の関数（MIDI 1.0 プロトコル）で受け、UMP をバイト列に戻します。クライアントは、自分のランループを持つスレッドで作ります。CoreMIDI の通知（ソースが消えたこと）はクライアントを作ったスレッドのランループに届くので、こうすればアプリのメインスレッドに頼りません。
  - CoreMIDI は、ポートを捨てている最中（`MIDIPortDispose`）にも受け取りのブロックを動かすことがあります。そこでブロックは自分の状態（`Receiver`）を共有で持ち、ポートを捨てる前にロックの中でそれを閉じます。閉じた後に届いたものは捨てるので、ポートが無くなった後は Brack に何も渡りません。
  - 同じ表示名のソースが複数あれば、CoreMIDI が機器ごとに保つ一意の ID の順に並べ、2 つめから「名前 (2)」などと名付けて、それぞれ開けるようにします。エンジンは消えたソースに気づき、戻ればつなぎ直します。
- **GUI。** GLFW の Cocoa 版と OpenGL 3.2 のコアプロファイルです。大きさはポイントで、Dear ImGui が Retina の解像度で描きます。ファイルダイアログは NSOpenPanel / NSSavePanel のシートで、その間も GUI は描き続けます。Brack.app（`NSHighResolutionCapable`）はプラグインホストを中に持ちます。
  - Brack.app の中のプラグインホストは、ビルドのたびに `bin` から写し直します（`brack_gui_hosts`）。Brack のリンクの後（`POST_BUILD`）に写すと、Brack をリンクし直さないビルドでは写らず、プラグインホストだけを作り直したときに古いものが残るためです。
  - GLFW の Cocoa 版のソースには `.m`（Objective-C）があるので、CMake では `OBJCXX` に加えて `OBJC` も有効にします。
  - Info.plist に、書類・デスクトップ・ダウンロード・外部とネットワークのボリュームを読む理由を書きました。プラグインホストの読み込みでも、macOS は Brack.app の名前で尋ねます。
- **署名。** Hardened Runtime で署名できます（`BRACK_CODESIGN_IDENTITY`、`cmake/brack.entitlements`）。ほかの開発元のプラグインを読むためにライブラリ検査を無効にし、JIT と署名の無い実行可能メモリを許します。権限無しで署名したプラグインホストは「different Team IDs」で拒まれます（ad hoc の署名で確かめた）。Brack.app は、中のプラグインホスト（`build-x64` から写した署名の無い x64 のものも）を先に署名します。
- **Rosetta 2（x64）。** Apple シリコンの Mac に Rosetta 2 を入れて確かめました。
  - arm64 の Brack から、x64 のテスト用シンセを x64 のプラグインホストで動かすと、arm64 のものとサンプル単位で同じ音が出ます。ネイティブのプロセスと Rosetta 2 のプロセスの間でも、`os_sync_wait_on_address` の共有メモリ用の待ち合わせが効きます。x64 のプラグインホストも、arm64 の Brack を強制終了すると一緒に終わり（kqueue）、エディタを開け、オーディオスレッドが time-constraint になります。
  - 1 ブロックの費用（64 フレーム、テスト用シンセ）は、x64 のプラグインホストでも arm64 のものより 1〜3 µs 多いだけです（プラグイン 1 つで、休みなく続けると 1.4〜1.5 µs、ブロックごとの時刻に処理すると 22〜23 µs）。主な費用は眠ったプラグインホストを起こすことで、テスト用シンセの計算はほとんど無いので、変換されたコードの計算の速さはこの数字に入っていません。
  - Apple シリコンでは、親が Rosetta 2 で動いていても arm64 のプログラムは動きます。そこで、ユニバーサル版の x64 の側（Rosetta 2）も、同梱する arm64 のプラグインホストで arm64 のプラグインを動かします。Apple シリコンかどうかは、ネイティブのプロセスでは `hw.optional.arm64`、Rosetta 2 で動くプロセスでは Apple が案内する `sysctl.proc_translated` で見ます（`appleSilicon()`）。
  - ユニバーサルなビルド（`CMAKE_OSX_ARCHITECTURES="arm64;x86_64"`）では、Brack.app、brack-cli、libbrack は両方入りで、プラグインホストはアーキテクチャごとに 1 つずつ作ります（Brack は名前で起動するため）。

### Windows（ARM64）

この節の計測と確認の環境は、Apple シリコンの Mac の VMware Fusion 上の Windows 11（ARM64）です。

- **ARM64EC と ARM64X の VST3**（`plugin_files.cpp` の `vst3ArchFolders`）。VST3 バンドルの `Contents/arm64ec-win` と `arm64x-win` のバイナリは、ARM64 の PC で動く x64 のプロセスにも読み込め、中のコードはネイティブで動きます。そこでバンドルの中で探すフォルダを、ビルドのアーキテクチャと PC のアーキテクチャ（`machineArchitecture()`。Windows では `IsWow64Process2` の本来のマシン、ほかの OS ではビルドと同じ）で決めます。x64 版が ARM64 の PC で動くときだけ、`arm64ec-win`、`arm64x-win`、`x86_64-win` の順に探します。x64 の PC の x64 版は `x86_64-win` だけ、arm64 版は `arm64x-win`、`arm64-win`（ARM64EC のコードは arm64 のプロセスには読み込めない）、x86 版は `x86-win` です。
  - アーキテクチャの名前（スキャンの一覧、GUI の `[VST3, x64]`、どのプラグインホストで動かすか）は、読み込むプロセスのものです。`arm64ec-win` だけのバンドルは、ARM64 の PC ではどのビルドから見ても「x64」で、x64 のプラグインホストに渡ります。x64 の PC ではどのアーキテクチャでもなく、一覧に載りません。`arm64x-win` だけのバンドルは、arm64 版からは「arm64」（自分で読み込む）、ARM64 の PC の x64 版・x86 版からは「x64」、x64 の PC からは「arm64」（動かないので断られる）です。「arm64ec」のような 4 つ目の名前にしなかったのは、アーキテクチャの名前がそのままプラグインホストの名前（`brack-host-x64.exe`）と同梱の表に使われているからです。
  - ARM64EC でビルドしたもの（`buildArchitecture()`、`CMakeLists.txt`）は x64 として扱います。周りから見れば x64 のコード（x64 のプロセスが読み込み、x64 のライブラリを読み込む）だからです。
  - 1 つのファイルの `.vst3`（バンドルでないもの）は、PE ヘッダーのマシン種別で決まります。ARM64EC のものは x64（ヘッダが 0x8664）、ARM64X のものは arm64（0xAA64）なので、x64 版の Brack は ARM64X の 1 ファイルのものを断ります。バンドルなら上のとおり読めます。
  - テスト用シンセの ARM64EC 版と ARM64X 版は `tools/arm64ec_synth.ps1` で作り（作り方は development.ja.md の「Windows で」）、`tools/arch_matrix.sh` の ARM64 の Windows の行はこの 2 つのバンドルも回します（無ければ「not run」）。
- **エミュレーションの費用**（`test_isolation --block-cost`。arm64 版の Brack から arm64・x64・x86 のテスト用シンセを動かした、5 回の中央値）。3 つとも同じ VM で動くので、arm64 のプラグインホストの値を VM の分とし、x64・x86 との差をエミュレーションの分とします。
  - ブロックを休みなく続けたとき、エミュレーションの分は x64 で 0〜4 µs、x86 で 2〜7 µs で、多くの条件で 5 回の幅が重なりました。たとえば 64 フレームでプラグイン 1 つなら、arm64 13.5 µs、x64 14.4 µs、x86 17.5 µs です。
  - プラグインホストの費用のほとんどは VM の分です。arm64 のプラグインホストでも 13.5〜74.5 µs（64 と 256 フレーム、プラグイン 1〜8 つ）かかり、64 フレーム 1 つでは、同じプロセスなら 1.1 µs、macOS の実機の別プロセスは 1.3 µs です。
  - 休みを挟んだとき（paced）は、同じ設定の 5 回で 4〜8 倍ばらつき（例: 64 フレーム 8 つの arm64 で 53〜196 µs）、アーキテクチャの差は幅に埋もれました。眠ったスレッドを起こす VM の遅れで決まっていて、VM では分けられません（13 章の TODO）。
- **x64 版の `ctest` の「Exception」。** `test_formats` が、負荷の下で終了コード 0xC0000409 で終わることがありました。プラグインホストが終わった後も、テストの一時フォルダのプラグインのファイルを Windows の何か（突き止めていない）が離さず、最後の `fs::remove_all` が投げた例外を誰も捕まえなかったためです。Brack 本体はプラグインのフォルダを消さないので、テストの削除だけを、エラーコードを返す形にしました。
- **x86 のエミュレーションの fast fail。** ARM64 の Windows の x86 のエミュレーションでは、CPU が fast fail を持ちません（`PF_FASTFAIL_AVAILABLE` が偽）。そこではテスト用シンセの `abort()` は、fast fail ではなく終了コード 3 で終わります。
- **プラグインホストの優先度の確かめ方。** プラグインホストは最初のブロックで MMCSS に入るので、`test_isolation` は優先度を測る間もブロックを処理させます。3 つのビルドとも優先度 24 になりました。
- **MIDI 入力の時刻（Windows MIDI Services）**（`midisrv_virtual_port.cpp`）。MSVC の `steady_clock::now()`（`__msvc_chrono.hpp`、MSVC 14.44）は、QPC の値を周波数で割った秒の整数部と余りに分けてナノ秒にします（10 MHz と 24 MHz は専用の分岐だが、値は同じ）。原点のずれはありません。同じ時計なので、仮想ポートのコールバックに来る時刻（QPC）を同じ割り算で `whenNs` にします。0（時刻無し）は 0 のままです。
  - QPC（この VM では 24 MHz）と steady_clock を交互に読んで比べると、差は読む間の時間の幅（±250 ns 以内）に収まり、10 秒たっても増えませんでした。
  - `tools/vmidi_probe` で WinMM から送ったメッセージには時刻が付き、その時刻は送った時刻の 36〜107 µs 後、コールバックの 10〜28 µs 前でした。
- **MIDI 入力の時刻（WinMM）**（`winmm_input.cpp`）。受け取ったときの時刻のままにします。MIDI Services のループバック（`loopMIDI Port 1`）に WinMM で送り、WinMM の入力で受けて、送った時刻と比べました。コールバックの中で読んだ steady_clock（今の Brack の時刻）は、送ってから平均 65〜69 µs 後で、1〜99 パーセンタイルの幅は 0.09〜0.11 ms でした。`midiInProc` の `dwParam2`（`midiInStart` からのミリ秒）を steady_clock に直したものは、幅が 0.90〜1.00 ms で、ミリ秒に切り捨てられるため送るより最大 0.95 ms 前になりました。
- **`tools/midi-timing` の Windows**（`MidiSrvSource.cs`）。Brack の仮想ポートと同じ MidiSrv の COM の ABI を C# から呼び、UMP に QPC の時刻を付けて送ります（`midi-zero` は 0）。送り先の選び方と使い方は development.ja.md の「MIDI の時刻を測る」にあります。VM の音声デバイス（High Definition Audio Device、48 kHz、周期 480 フレーム）では、揺れの幅（1 秒目からの 1〜99 パーセンタイルの幅）は、どの送り方でも共有モードで 5.5〜10.1 ms、排他モードで 0.6〜3.5 ms でした。
  - どの回も送ったものはすべて届き、送った順より前に届いたものはありませんでした。`midi-ahead` では、MidiSrv が時刻まで待ってから渡しました。
  - 揺れは VM の音声デバイスで決まっていると見ています。共有モードの `now` は、周期を 128、480、1920 フレームにすると 9.8 ms、5.5 ms、9.9 ms で周期によらず、同じ設定でも回ごとに 5.5〜9.8 ms と変わったためです。x64 の PC の実機での値は、下の「Windows（x64）」にあります。
- **`test_virtual_midi`**（手で回すもの）。この VM の MidiSrv（`Midi2.VirtualMidiTransport.dll` 1.0.15）は microsoft/MIDI#1047 の修正の前ですが、仮想ポートを作って消すことを 10 回繰り返しても、サービスは毎回応えました。x86 版は「Windows MIDI Services client (Midi2.MidiSrvTransport) not available: 0x80040154」で失敗します。ARM64 の Windows 11 では、32 ビットの COM の登録が `SysWOW64\Midi2.MidiSrvTransport.dll` を指すのに、そのファイルがありません。Brack の `isAvailable` はこれに「this 32-bit Brack needs a 32-bit client」と答えるので、直すものはありません。
- **GUI。** ARM64 のプログラムには VM のディスプレイドライバー（VMware SVGA 3D、D3D11 まで）の OpenGL が無く、GUI は OpenGL 3 の窓を作れませんでした。x64 版の GUI は、同じ VM でそのまま開きました。回避は development.ja.md の「Windows で」にあります。
  - 窓が作れなければ、GUI は GLFW の理由（例:「cannot open an OpenGL 3 window: WGL: The driver does not appear to support OpenGL」）を出して終わります。Windows ではコンソールが無いのでメッセージボックスに、ほかの OS では標準エラーに出します。

### Windows（x64）

x64 の PC（i9-13900K、Windows 11）の実機で確かめたことです。

- **組み合わせの表**（`tools/arch_matrix.sh` の `windows_x64`）。x64 版と x86 版を、互いの 3 形式、ARM64 版（クロスビルド）の 3 形式、ARM64EC と ARM64X の VST3 で回します。
  - ARM64EC の VST3（`arm64ec-win` だけのバンドル）は一覧に載らず（上の「Windows（ARM64）」）、読み込むと「no x64 binary in the bundle (x86_64-win)」（x86 版は `x86-win`）で断られます。表はこれを `<フォルダ>=no-binary` で期待し、期待を付けずにこの理由で断られれば誤りにします。
- **x86 版の仮想ポート。** x64 の PC の Windows 11 にも 32 ビットの MIDI Services のクライアント（`SysWOW64\Midi2.MidiSrvTransport.dll`）は無く、x86 版は仮想ポートを作れませんでした（0x80040154）。ARM64 の Windows と同じなので今の Windows の状態とみなし、Brack では何もしません（`isAvailable` がそう答える）。この PC の MidiSrv（1.0.15）は microsoft/MIDI#1047 の修正の前なので、仮想ポートを作って消すもの（x64 版の `test_virtual_midi`、`tools/midi-timing` の `midi-ahead`）は回していません。
- **MIDI の時刻（`tools/midi-timing`）。** この PC の出力は Bluetooth のヘッドホン（A2DP、48 kHz）だけです。`now` と `ahead` を、共有モードと排他モード（この出力でも開けた）で回しました。この出力で開いた直後に約 11.5 ms の段差が出ることと、それに合わせた `ArrivalClock` の規則は 12 章にあります。
  - 今の実装では、周期 480 フレームの揺れの幅（1500 個ずつ、1 秒目からの 1〜99 パーセンタイルの幅）は、共有モードで 0.02〜0.07 ms、排他モードで 0.03〜0.41 ms でした。どの回も 1500 個すべてが届き、入れ替わりは 0 でした。共有モードの周期は、128 を頼んでも 480 になりました（共有モードのエンジンの 10 ms）。
  - VM（上の「Windows（ARM64）」）の `now` と `ahead` より、ほとんどの回で 1 桁以上小さく、VM の揺れは VM の音声デバイスで決まっていたという見立てと合います。
  - **MIDI ポートから。** loopMIDI（teVirtualMIDI）のポートは、MIDI Services には「teVirtualMIDI - Virtual MIDI Driver x64」という 1 つのエンドポイントのグループとして見え、名前で探す `MidiSrvSource` は見つけられません。そうすると Brack の仮想ポートを作ってしまうので（この PC では避けたい。上の「x86 版の仮想ポート」）、`tools/midi-timing` は同じ名前の WinMM の出力があればそこから送ります（`WinMmSource`）。WinMM は時刻を付けずにすぐ送るので、`midi` と `midi-zero` は同じ送り方になり、`midi-ahead` は回せません。
  - 別の Bluetooth のヘッドホン（48 kHz、周期 480）で `loopMIDI Port 1` から送ると、揺れの幅は `midi` と `midi-zero` で 0.13〜0.37 ms、`now` で 0.02〜0.03 ms（排他モードの 1 回だけ 0.46 ms）で、どの回もすべて届き、入れ替わりは 0 でした。WinMM の入力の時刻は Brack がコールバックの中で読む steady_clock（上の「MIDI 入力の時刻（WinMM）」）なので、loopMIDI と MidiSrv を通るぶん、`now` より 0.1〜0.3 ms 広くなります。
